# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A personal finance tool (in French — user-facing strings, comments, and category names should be in French) for syncing transactions from 3 personal bank accounts, categorizing them, and generating budget/savings reports.

This is a pnpm + Turborepo monorepo (migrated from the single-package `budget-tracker` CLI tool). It reuses the same business pipeline (Enable Banking → import → categorize → PostgreSQL → transactions table) but split across workspace packages and apps.

## Architecture

- `@budget/db` — schéma Drizzle + `pg`, base **`budget_t3`**. Le cloisonnement par espace est décrit dans « Espaces (multi-utilisateurs) » plus bas.
- `@budget/api` — **tout est piloté depuis la webapp, il n'y a plus aucun script CLI** (`scripts/` a disparu). Organisation en dossiers par domaine sous `src/` :
  - `router/` — adaptateurs tRPC uniquement (`auth`, `transactions`, `categories`, `connections`, `settings`, `sync`) : schéma zod d'entrée + délégation, aucune requête SQL. **Y remettre de la logique métier est une régression.**
  - `banking/` — Enable Banking : `client.ts`, `domain.ts`, `settings.ts`, `connections.ts`, `fetch-transactions.ts`.
  - `transactions/` — `normalize.ts`, `import.ts`, `queries.ts`, `internal-transfers.ts`.
  - **Virements internes** (`transactions/internal-transfers.ts`, spec du 2026-08-03 dans `docs/superpowers/specs/`) — un virement d'un compte suivi à un autre produit deux lignes qui gonflaient entrées _et_ sorties (~20 % des flux affichés). `detectInternalTransfers()` les apparie (`transactions.transfer_pair_id`, auto-référence) après chaque import, sur **toute** la table et non les seules lignes importées : la moyenne de référence porte sur 12 mois, un mois propre comparé à des mois gonflés inventerait un écart. `transfer_source` a le même contrat que `category_source` — `manual` (paire posée ou _retirée_ à la main) n'est jamais réécrit.
    - Le signal décisif est **négatif** : un IBAN de contrepartie renseigné qui ne désigne pas le compte de la jumelle refuse la paire. C'est lui qui sépare un apport interne d'un virement de même montant, le même jour, sur le même compte, venu d'un compte non connecté. `mcc` est vide sur 100 % des lignes : c'est `bank_code` qui sert de veto carte/retrait/prélèvement, et en **liste noire** — SG ne renseigne pas ce champ, une liste blanche l'exclurait de la détection.
    - **Une paire n'est neutralisée que si ses deux jambes sont dans les comptes sélectionnés** (`twinWithinScope`, `transactions/queries.ts`). Seul `bank` est ré-appliqué à la jumelle : les paires vont jusqu'à 3 jours d'écart, donc à cheval sur deux mois — mettre les dates dans le périmètre déplacerait l'artefact sur la frontière de mois au lieu de le supprimer. La propriété que cette règle garantit : le solde affiché égale la variation réelle des comptes affichés, quelle que soit la sélection.
    - Tous les agrégats les écartent **en dur**, sans consulter le param `internes` (qui ne gouverne que le relevé) — sauf `bankCounts`, qui compte des lignes et annonce ce que la table affichera une fois le compte coché : son périmètre est « tous les comptes » alors que le clic va le restreindre, l'exclusion y ferait annoncer 2 pour une table de 3 lignes.
  - `categorization/` — `prompt.ts`, `results.ts`, `similar.ts`, `run.ts`.
  - `categories/` — `queries.ts`, `mutations.ts`, `budgets.ts`, `suggestions/{analyze,apply,schema,replace-plan}.ts`.
  - `pipeline.ts` — `performSync` / `performImport`, cross-domaine. `lib/` ne garde que le transverse (`data-dir.ts`, `single-flight.ts`).

  Le sens des dépendances est `router/` → domaines → `lib/`, jamais l'inverse : c'est l'inversion `src/lib/` → `scripts/` qui avait imposé les suffixes `-core`, tous supprimés. Les services importent `db` directement (même singleton que `ctx.db`, voir `trpc.ts`). `lib/single-flight.ts` sérialise les opérations longues : clé `sync` (sync + import) et clé `categorize`, partagée entre la catégorisation déclenchée par le pipeline et celle déclenchée depuis l'UI.

  Deux pièges de configuration liés à la disparition de `scripts/` : `tsconfig.include` vaut `["src"]`, donc `tsc` émet `dist/index.d.ts` (et non `dist/src/…`) — `exports.types` doit suivre, sinon les apps ne résolvent plus les types de `@budget/api`. Et l'exception eslint sur les règles `no-unsafe-*` (code Enable Banking porté, `ebApi` non typé) nomme ses fichiers un par un : ne jamais la remplacer par un glob de dossier, elle exempterait silencieusement du code neuf.
  - **Catégories intelligentes** (arborescence parent/enfant, `categories.parent_id`) : le routeur `categoriesRouter` expose `tree` (arborescence complète) en plus de `list`.
    - **Suggestions** (`src/categories/suggestions/`) — un LLM (`claude-haiku-4-5`) analyse un échantillon de transactions récentes (6 derniers mois, max 500) et propose une arborescence parent → sous-catégories avec les `txnIds` correspondants, exposée via `categoriesRouter.suggestions.{generate,accept,apply}` et la page `/categories` (`apps/tanstack-start`). **Le serveur ne retient rien du run** : `generate` renvoie `{ suggestions, sample }` et c'est la page qui les garde, dans un `useState` (`SuggestionsRun`, `routes/_authed/categories/index.tsx`). Quitter la page ou recharger perd la proposition, et c'est assumé — elle n'écrit rien en base, relancer coûte un appel LLM et jamais une incohérence. Il n'y a donc **ni procédure `status` ni état par espace côté serveur** (l'échantillon analysé est de la donnée de foyer, elle n'a pas à séjourner dans la mémoire du process) : ne pas les réintroduire sans les persister d'abord. Corollaire retiré avec eux : le bandeau « N nouvelles transactions arrivées depuis » n'existe plus, la proposition et la page ayant désormais la même durée de vie. L'analyse se déclenche depuis l'UI (`/categories`) — il n'y a plus de commande CLI.
      - **Le prompt part de l'arborescence réelle, et la réponse attendue est l'arbre complet.** `buildAnalysisPrompt(txns, tree)` reçoit `listCategoryTree()` et l'échantillon porte la catégorie actuelle de chaque transaction (`category` / `parentCategory`, `null` pour une orpheline) — sans quoi le LLM ne voit aucun nom existant et propose des **variantes** de l'existant (« Transports » face à « Transport », « Sante » face à « Santé ») : `categories.name` est unique dans l'espace mais sensible à la casse et aux accents, donc rien en base n'arrête le doublon, et l'UI l'affiche comme une nouvelle parente à créer. D'où la règle « réutilise les noms existants au caractère près » en tête des consignes. Le corollaire à ne jamais inverser : la réponse doit rester l'arborescence **entière** (existant repris + nouveautés), **jamais un delta** — `applySuggestions` en mode `replace` traite la proposition comme la nouvelle vérité et supprime tout ce qui en est absent. Un prompt demandant « seulement ce qui manque » ferait de `replace` un bouton de suppression de masse. Côté app, `deriveSuggestions` compare les noms accents/casse/espaces insensibles et, quand une parente existe, fait porter au `GhostBranch` **le nom de la base** et non la chaîne du LLM : c'est lui qui repart dans `accept`, où `upsertCategory` fait un `eq(categories.name, …)` exact. Ce filet ne dépluralise pas (« Frais », « Cours », « Revenus » le mettraient en défaut) — une greffe erronée est silencieuse, un doublon proposé reste visible et écartable.
      - **`accept` (une branche) et `apply` (tout l'arbre) ne sont pas deux tailles du même geste.** `applySuggestions` a un effet de bord qui n'est visible ni dans son nom ni dans l'UI : **dans les deux modes**, y compris `merge` (présenté comme purement additif), toutes les transactions à `category_source = 'llm'` repassent à `category_id = NULL` avant une re-catégorisation complète — seules les `manual` survivent. Un apply coûte donc une passe LLM entière, et son échec est avalé dans un `console.error` (`apply.ts`) alors que l'UI a déjà navigué ailleurs. C'est exactement pourquoi `acceptSuggestion` existe **à côté** et n'appelle pas `applySuggestions` sur un tableau à un élément : elle crée le parent manquant et la sous-catégorie, puis range les `txnIds` **encore `category_id IS NULL`** en `category_source = 'auto'`, sans reset global ni appel LLM. Le garde `IS NULL` est ce qui rend vraie la promesse de l'écran (« rien de ce qui est déjà rangé n'est remis en question ») : l'échantillon analysé contient aussi des transactions déjà classées. Câbler le bouton « Ajouter » sur `apply` défausserait le classement de toute la base à chaque clic.
      - **L'UI de la page est en « Direction C »** (maquette du 2026-07-28) : plus d'écran de relecture ni de bascule fusionner/remplacer — les branches proposées sont posées **dans la liste**, sous la parente concernée, et se répondent une par une (« Ajouter » / « Écarter »). Le rejet est purement local (rien à écrire pour dire non). `deriveSuggestions` (`routes/_authed/categories/-lib/suggestions.ts`) croise la proposition avec l'arbre réel et n'affiche que ce qui manque : une catégorie dont le nom existe déjà n'est jamais une proposition (`categories.name` est unique dans l'espace, et l'analyse re-propose massivement l'existant — c'est même son rôle). Les procédures `apply`/`previewReplace` et leur mode `replace` restent en place et testées, mais **plus aucune UI ne les appelle** : c'est la seule voie de vraie restructuration, à ne pas supprimer sans décision explicite.
      - **Identité d'une parente = couleur + icône**, choisies dans la modale de `/categories` et nulle part ailleurs. `categories.icon` stocke un nom Lucide du jeu fermé `CATEGORY_ICON_GROUPS` (`@budget/shared/src/icons.ts` : noms + mots-clés français, **jamais de composant** — y importer `lucide-react` ferait entrer la librairie dans un package dont la seule dépendance runtime est `zod`) ; la table nom → composant vit côté app (`-components/category-icon.tsx`), explicite plutôt qu'un `import * as lucide` qui embarquerait ~1500 icônes. Même règle que `color` : **seule une parente** en a une (`updateCategoryIcon` le garde), une sous-catégorie se lit dans la famille de son parent. La palette est fermée à 13 teintes pour un nombre illimité de parentes : **une collision de teinte est un état normal**, signalée (pastille « déjà prise », note « même teinte que… ») et jamais interdite — c'est l'icône qui distingue les deux.
    - **Catégorisation few-shot** (`src/categorization/similar.ts`, `prompt.ts`, `results.ts`) — avant l'appel LLM, `findSimilar()` cherche des transactions déjà catégorisées proches (contrepartie exacte > trigrammes `pg_trgm` sur la description > MCC > `bank_code` discriminant en dernier recours) et les injecte comme exemples dans le prompt (`buildFewShotPrompt`). Fallback silencieux vers le prompt générique si aucune similaire trouvée. Nécessite l'extension PostgreSQL `pg_trgm` (voir plus bas). Ces exemples sont des **indices, pas une autorité** : le tier de repli `bank_code`/MCC est très générique (ex. `C2` = « virement reçu » chez SG) et remonte des exemples hétéroclites — le prompt demande explicitement de ne classer par analogie que si la transaction est de même nature.
      - **La similarité prime sur la priorité manuelle dans le tier trigramme.** `manualFirst` (préférer un exemple corrigé à la main) est le premier critère de tri des tiers contrepartie/MCC/`bank_code`, où tous les candidats sont également similaires — mais dans le tier trigramme il ne départage qu'**à l'intérieur d'une bande** de similarité (`round(sim, 1)`). Le remettre en tête y est une régression silencieuse : mesuré sur les données réelles, une correction manuelle faiblement similaire passait devant un quasi-doublon et le meilleur exemple injecté tombait à 69,5 % de bonne catégorie parente, contre 95,8 % avec le tri actuel.
      - **Seuil trigramme à 0,5** (`TRIGRAM_THRESHOLD`), calibré sur les données réelles et non sur une intuition : les libellés bancaires sont dominés par du boilerplate (`CB `, `FACT`, padding, chiffres de date), au point que deux commerçants sans rapport atteignent 0,38. Sous 0,5, l'accord de catégorie parente ne dépasse quasiment pas celui de deux transactions au hasard (19 % contre 15 %). Ce seuil est calibré sur les trois banques actuelles — un établissement au format de libellé moins répétitif le rendrait inutilement strict.
      - **Court-circuit déterministe** (`resolveShortcut`, `results.ts`) — quand au moins 2 similaires partagent la contrepartie de la transaction à classer **et** la même catégorie, elle est catégorisée sans appel LLM (`categorySource = 'auto'`). La comparaison à la contrepartie de la transaction est la garde essentielle : la liste reçue est la **fusion de tous les tiers**, pas seulement du tier contrepartie exacte. Sans elle, deux candidats trigramme partageant une contrepartie _entre eux_ suffisaient à catégoriser d'autorité une transaction qui n'en a aucune — cas majoritaire (57 % des transactions en base), et donc court-circuit de la seule étape capable de rattraper un match faible.
    - **Ne jamais coder en dur un nom de catégorie dans le prompt** (`buildSystemPrompt`) — la catégorisation ne s'appuie que sur les catégories réellement présentes en base. Une règle citant une catégorie absente de la liste (le prompt mentionnait « Revenus », « Autres », « Apport Alex » après un remplacement d'arborescence) fait répondre le LLM hors liste ; la réponse est rejetée et la transaction n'est **jamais** catégorisée, à chaque run. Quand aucune catégorie existante ne convient, le LLM répond `categorie: null` : `partitionResults` sépare ces refus assumés (`declined`) des réponses aberrantes (`rejected`, catégorie inconnue ou id hors lot), et `categorization/run.ts` logue les deux — ne jamais les confondre ni les avaler en silence, c'est ce qui rendait le désalignement invisible.
    - **Les deux process se complètent** : la catégorisation classe avec l'existant, les suggestions créent ce qui manque. C'est `sampleTransactions` (`categories/suggestions/analyze.ts`) qui ferme la boucle, par un **échantillon stratifié** plafonné à `SAMPLE_LIMIT` : d'abord les transactions sans catégorie, **sans fenêtre de date** (une orpheline ancienne reste un trou de l'arborescence) et dans la limite de `UNCATEGORIZED_SAMPLE_SHARE` (30 %), puis complété par les transactions récentes déjà catégorisées, qui donnent le contexte des habitudes réelles. Les deux moitiés sont indispensables et le plafond n'est pas cosmétique : sans la première, les orphelines (~2 % des lignes) seraient évincées dès que le volume dépasse la limite et la boucle ne se refermerait jamais ; sans la seconde, le LLM proposerait un arbre ne couvrant que les orphelines, et le mode `replace` supprimerait tout le reste — `computeReplacePlan` ne protège que les corrections manuelles.
  - **Budgets par catégorie** (`categories/budgets.ts`, table `category_budgets`, routeur `categories.budgets.*`, maquette du 2026-08-05) — la maquette en fait **un second onglet de `/categories`** ; c'est une **route à part, `/budgets`** (troisième écran de réglages, à côté de `/categories` et `/banques`, atteint par le menu de l'engrenage — d'où `SETTINGS_TITLES` dans `AppHeader` plutôt qu'un ternaire à deux valeurs). Décision de découpage, pas de portage : monté en onglet, `CategoryOverviewTree` devait porter deux jeux de colonnes, deux grilles et une douzaine de conditions de mode. `BudgetTree` (`routes/_authed/budgets/-components/`) affiche la **même liste en lecture** — mêmes plis, même badge d'identité, mêmes paliers de teinte — et n'y rend éditables que les montants : renommer, recolorier, ajouter, supprimer et répondre aux propositions restent sur `/categories`. C'est ce qui le tient à ~350 lignes sans toucher à l'existant. Il lit `categories.tree` (et non `overview`, dont les compteurs de transactions ne servent à rien ici).
    - Un budget est un **montant mensuel sans dimension de mois** : une ligne par catégorie, `set` écrase, rien à versionner, pas de report du non consommé. Une parente peut être **détaillée** (`category_budgets.detailed`) : ce sont alors ses sous-catégories qui portent les montants et elle n'affiche que leur somme. `budgetSlots` est la **seule** définition de « poste » — parente globale, ou ses enfants si détaillée — et les trois compteurs d'en-tête, le « N sans budget » et le bandeau « tout est budgété » en sortent tous, donc ils ne peuvent pas se contredire. Une parente sans sous-catégorie reste globale quel que soit son drapeau, sinon son budget disparaîtrait de l'écran mais pas des compteurs. Repasser une parente en « Global » **ne supprime pas** les montants de ses enfants : ils cessent de compter, un aller-retour ne les perd pas.
    - La proposition (« Moyenne 510 € → ») est la moyenne des **6 derniers mois complets**, mois en cours exclu, débits seuls, virements internes écartés (`transfer_pair_id IS NULL` suffit : le périmètre est « tous les comptes », les deux jambes y sont toujours). Elle porte sur 6 et non sur les seuls mois actifs — un poste vu 5 mois sur 6 dépense en moyenne moins qu'un poste mensuel. **Moins de 4 mois actifs sur 6 = pas de proposition** (`irregular`) : la moyenne reste affichée, c'est un fait, mais le bouton de pré-remplissage disparaît. Une catégorie de revenus n'a donc aucune proposition (débits seuls) sans être exclue de la liste — la maquette ne les distingue pas.
    - Trois blocs de la maquette sont des conteneurs `display:none`, comme les Directions A/B plus haut, et ne sont **pas** portés : le bandeau « N postes sans budget » avec ses bases (moyenne / médiane / mois le plus bas) et son « Remplir les N » — d'où la base **toujours** « moyenne 6 mois », seule atteignable —, les sparklines de 6 mois sur chaque ligne, et le « réel moy. » des parentes. Seul le bandeau vert « Tous vos postes ont un budget » est vivant, et il porte l'unique « Tout vider ». La note de bas de page de la maquette annonce un mois de départ (« s'applique à partir d'août 2026 ») : rien ne le porte en base, la note affichée ne dit que d'où vient la moyenne et pourquoi certains postes n'en reçoivent pas.
    - **La revue consomme ces budgets depuis le 2026-08-06** (maquette : `Revue du mois.dc.html` et `Transactions.dc.html` ont reçu la même rangée « Budget » et les mêmes jauges). `attachBudgets` (`~/lib/revue-budgets.ts`) est le seul endroit qui les croise avec la dépense ; le loader de `_revue` l'appelle et pose sur chaque `RevueCategory` son `budget` et sa part `covered`.
      - **Deux axes, et c'est l'unique réglage de `BudgetGauge`** (prop `scale`, révision de maquette du 2026-08-07 : `jaugeEch`/`jaugeHachee` + `catScale`/`subScale` dans `Revue du mois.dc.html`, repère de budget dans `Breakdown.dc.html`).
        - **Axe propre** (`scale` absent) — bandeau et poste ouvert : la piste *est* le poste, sa longueur vaut `max(consommé, budget) + hors budget`. Le bord droit est donc le budget tant qu'on ne l'a pas dépassé, les hachures se posent après lui et le reste à dépenser est de la piste vide. `KpiBand.dc.html` n'a pas bougé d'un octet à cette révision : ces deux jauges-là gardent la géométrie d'origine, elles sont seules à l'écran et n'ont rien à quoi se comparer.
        - **Axe partagé** (`scale` fourni) — la colonne des postes : `breakdownScale` = le plus grand entre la plus grosse dépense et le plus gros budget de la liste, pour **toutes** les lignes. Sans lui, une jauge calée sur son propre budget peint un poste à 10 € aussi long qu'un poste à 1 700 € juste au-dessus et la colonne cesse de se lire de haut en bas. Deux conséquences à ne pas défaire : les segments sont **contigus depuis zéro** et s'arrêtent à la dépense — les hachures démarrent à la fin du **couvert**, pas à la fin du budget, sinon un poste sous-consommé se peindrait plus long qu'il n'a dépensé ; et le budget, qui n'est plus le bord droit de la piste, porte un **repère** (trait de 1,5 × 11 px, `--fg` à 55 %, `title="Budget"`). Il déborde la piste en haut et en bas : il est posé par `BreakdownRow`, jamais par `BudgetGauge`, qui découpe la sienne (`overflow-hidden`).
      - **Dans la colonne de la revue, chaque ligne est une jauge** — y compris celles que rien ne budgète, y compris quand la comparaison est écartée. `BreakdownItem.budget` est **posé sur toutes les lignes**, `amount: null` valant « rien ne budgète ceci, peins la seule dépense » : sans ça la colonne changerait de gabarit le jour où le premier budget est saisi. D'où deux bascules distinctes, à ne pas fusionner : `gauged` (une ligne porte le vocabulaire) commande les 44 px et la piste de 7 px, `captioned` (une ligne a un budget *chiffré*) ouvre la colonne de reste de 74 px. `/transactions` ne pose `budget` sur aucune ligne et garde donc la barre de répartition de 3 px.
        - Le segment « à classer » d'une parente **détaillée** est le seul cas à `covered: 0` : c'est de la dépense qu'aucun budget ne peut atteindre, elle part donc entièrement en hachures grises (`jaugeHachee`). Sous une parente **globale** il est couvert comme le reste et se lit comme n'importe quelle ligne — il garde alors la trame dans la teinte du poste, extension du portage que la maquette n'a pas.
      - **Trois raisons, et trois seulement, de ne rien comparer**, chacune avec sa phrase dans la rangée « Budget » plutôt qu'une rangée qui disparaît (`BUDGETS_OFF_MESSAGES`) : aucun budget posé (`plan.budgeted === 0`, prioritaire) ; un **filtre de comptes actif** — un budget ne connaît pas les comptes, comparé à une sélection il ferait passer chaque poste sous son budget sans que rien n'ait changé ; une **période qui n'est pas faite de mois calendaires pleins** — `wholeMonths` rend le multiplicateur, `0` sur « 30 derniers jours ». Le test du filtre porte sur la **présence** de `search.bank`, jamais sur « tous les comptes sont cochés » : `toggleBank` retombe sur `undefined` dès que la sélection est complète.
      - **Les montants viennent de `budgets.plan`, les décomptes de ce qui est affiché.** L'enveloppe du bandeau et le « N postes budgétés sur M » sont `plan.total`/`budgeted`/`slots` × mois, à l'échelle de l'espace : un poste budgété sans dépense ce mois-ci ne doit pas rétrécir l'enveloppe, et `/budgets` affiche alors exactement les mêmes nombres. Même règle sur une parente détaillée — son budget est la somme de **toutes** ses sous-catégories budgétées, y compris celles absentes de la période, sinon il ne serait pas la somme des jauges de la colonne. Seul `covered` sort de la période.
      - Le repère d'**allure du mois** (`pace`, trait vertical au prorata des jours écoulés) et sa légende ne sont pas portés, et ce n'est pas un oubli de code mort : c'est la réponse de la maquette à la question 4 du brief du 2026-08-06 (`docs/superpowers/specs/`) — elle le calcule, puis passe `pace` à `null` et masque la légende. La revue montre le **consommé brut**, sur un mois en cours comme sur un mois passé. Le rétablir demande de trancher ce qu'il devient sur un mois révolu, où il n'a plus de sens.
      - **Quatre écarts assumés avec la maquette**, tous par contrainte de ce que les données ou le partage des composants imposent. (1) Le chiffre de droite de la rangée « Budget » (« reste 45 € ») se retire sous `xl`, alors que `budFoot` est inconditionnel dans `KpiBand.dc.html` : les mentions « vs moy. » des deux rangées de flux se retirent déjà là, et les garder toutes les trois désalignerait la jauge des barres au-dessus d'elle. Le segment rouge du dépassement, lui, ne se cache jamais. (2) La colonne de `/transactions` n'a pas reçu les jauges — `Transactions.dc.html` les a, c'est un autre portage. (3) `KpiFocus` en a une **sur les deux écrans**, alors que le bloc `fc` de `Transactions.dc.html` s'arrête à l'écart à la moyenne : il est monté par le layout, comme le bandeau, et l'en séparer coûterait un prop de plus pour un écart d'un composant. (4) Un **poste budgété sans aucune dépense sur la période** (état que le brief demande de prévoir) n'a pas de ligne dans la colonne : `transactions.byCategory` ne remonte que les catégories qui ont bougé. Son budget compte quand même dans l'enveloppe et dans le « N postes budgétés sur M » — lui donner une ligne voudrait dire fusionner l'arborescence dans la source de la colonne, ce qui touche aussi l'anneau et son décompte de postes.

Refonte du 2026-08-04 : la barre a quitté le **fond** de la ligne (teinte à 42 % derrière le texte) pour une rangée à elle, 3 px sous l'intitulé, **pleinement saturée** sur une piste `border-strong/60` — la maquette le motive par la lisibilité de l'intitulé. Deux conséquences : plus rien n'est en position absolue dans la ligne, et le survol prend `--accent` (le rôle _fond de survol_) et non `--surface2`. La barre glisse d'une largeur à l'autre (260 ms), et **deux détails conditionnent l'existence même de cette transition** — sans eux le CSS est bien posé mais ne se déclenche jamais, React remontant chaque ligne à sa largeur finale : la clé est la **position** dans la liste et non le nom (il change à chaque niveau), et la ligne est **toujours un `<button>`**, `disabled` quand elle ne se creuse pas, jamais un `<div>` selon le cas (React ne réutilise pas un nœud dont le type d'élément change, et descendre dans un poste fait justement passer toutes les lignes en lecture seule). La largeur de la colonne est passée à **254 px**, à tenir alignée avec celle de `KpiFocus` (voir `rdStackPx === listPx` plus haut).
    - La liste des catégories de la revue (aujourd'hui `breakdown-list.tsx`) est triée par montant décroissant, sans contrôle : le tri « Écart vs moy. » / « À classer » et son search param `catSort` ont été retirés le 2026-07-28 (avec `categoryAverages`, son seul consommateur). Ne pas les remettre sans demande explicite.
### App mobile — supprimée le 2026-08-07

`apps/expo` (gluestack-ui v5 + nativewind) était **en suspens depuis le 2026-07-23** : l'objectif restait une vraie app universelle web+native, ce que gluestack ne permet pas correctement. Deux semaines plus tard elle n'avait toujours pas repris, et 5 600 lignes gelées plus 52 dépendances pesaient sur chaque `pnpm install`, chaque `turbo run` et chaque relecture — elle a été supprimée, avec `tooling/tailwind` dont elle était le seul consommateur. `git log` la rend : partir de là plutôt que de la réécrire, mais **sans reprendre gluestack**, qui est la raison du gel.

Deux traces subsistent volontairement, sans consommateur aujourd'hui : le CORS + `trustedOrigins` better-auth ouverts à `localhost:*` en dev (`apps/tanstack-start/src/lib/cors.ts`, `src/auth/server.ts`) et le `host: true` du `vite.config.ts`, qui laissaient le téléphone atteindre l'API en LAN. Inoffensifs en dev, et exactement ce qu'il faudrait remettre.

Pipeline métier inchangé : connexions bancaires configurées dans l'app (`/banques` : onboarding Enable Banking, wizard d'ajout, callback OAuth sur `/callback`, sessions stockées en DB) → sync → `data/<orgId>/*.json` (racine du monorepo, un répertoire par espace) → import (`packages/api/src/transactions/import.ts`) → PostgreSQL → tRPC (`@budget/api` routers) → table des transactions (`apps/tanstack-start`).

## Espaces (multi-utilisateurs) — cloisonnement

L'app est multi-utilisateurs depuis le 2026-08-05. L'unité de cloisonnement est l'**espace** : un utilisateur seul, ou un foyer partagé. Un espace **est** une `organization` du plugin `organization` de better-auth — pas de table maison : le plugin apporte `organization` / `member` / `invitation`, les rôles, le flux d'invitation, et surtout `session.active_organization_id`, ce qui fait vivre l'espace courant **dans la session et non dans l'URL**. C'est pour ça qu'aucune route n'a de segment d'espace et que le portage n'a touché aucun loader.

- **Ce qui porte un `organization_id`** : `bank_connections`, `auth_requests`, `bank_accounts`, `categories`. Pas `transactions` — leur espace se lit par leur compte, et presque toutes les requêtes joignaient déjà `bank_accounts`. Ne pas dénormaliser : ce serait une seconde vérité pouvant diverger du compte. Pas `category_budgets` non plus (via sa catégorie). Pas `app_settings`, qui est la configuration Enable Banking de l'**installation** — une par déploiement, pas une par foyer.
- **Les catégories appartiennent à l'espace, jamais au compte bancaire.** Toute l'app agrège _par catégorie, à travers les comptes_ : le compte est un périmètre de lecture. Et **un compte appartient à exactement un espace** — partager un compte = ajouter un membre à l'espace. C'est ce qui permet à `transactions.category_id` de rester une seule colonne ; une table `transaction_categories` par espace multiplierait chaque agrégat et chaque passe LLM par le nombre d'espaces. À ne pas rouvrir sans décision explicite.
- **`categories.name` n'est unique que dans l'espace** (`UNIQUE(organization_id, name)`), idem `accounts.uid` — deux membres d'un couple qui connectent chacun le même compte joint peuvent recevoir le même uid d'Enable Banking, une unicité globale ferait échouer le second sans rien expliquer. Tout ce qui résout une catégorie par son nom (`upsertCategory`, `setTransactionCategory`, le filtre `category` de l'URL, l'`onConflict` de `apply.ts`) doit porter l'espace.
- **Le point de passage est `orgProcedure`** (`packages/api/src/trpc.ts`) : elle lit `session.activeOrganizationId` — **jamais un input** — et revérifie l'appartenance à chaque requête, pour qu'une exclusion prenne effet sans attendre l'expiration de la session. Chaque service reçoit l'`organizationId` en **premier paramètre**. Côté transactions, le filtre commun `transactionsFilterQuery(organizationId, query)` pose la condition avant tout filtre d'URL ; trois requêtes ne passent pas par lui et ont dû recevoir leur `innerJoin(accounts)` : les stats de sens dominant de `reviewQueue`, le décompte de `categorization/run.ts`, et les cinq requêtes de `categorization/similar.ts` — sans quoi le few-shot injecterait les transactions d'un autre foyer comme exemples dans le prompt (fuite _et_ dégradation).
- **Les mutations par id sont des IDOR en puissance** : tout id venant du client (`setTransactionCategory`, `removeCategory`, `setCategoryBudget`, `revokeConnection`, `acceptSuggestion`…) porte l'espace dans son `WHERE`, et pour les écritures sur `transactions` c'est `ownedByOrganization()` (`EXISTS` corrélé — un `UPDATE` n'a pas de `FROM bank_accounts`). Attention au **succès silencieux** : un `UPDATE` qui ne touche aucune ligne ne lève rien, d'où la vérification explicite en amont là où l'UI attend une confirmation (`renameCategory`).
- **Les états hors base sont scopés eux aussi**, et c'est le genre de fuite qu'aucun `WHERE` ne rattrape : les verrous `single-flight` valent `sync:${orgId}` / `categorize:${orgId}`, et les JSON Enable Banking vivent dans `data/<orgId>/`. Le troisième — l'état des suggestions — a été supprimé plutôt que scopé : il vit maintenant côté navigateur (voir « Suggestions » plus haut). Ce dernier point n'est pas du rangement : `importTransactions` lit _tout_ le répertoire qu'on lui donne — à plat, un import déclenché par un espace avalerait les fichiers d'un autre et le verrou par espace deviendrait un mensonge.
- **Inscription sur invitation** (`databaseHooks.user.create.before`, `@budget/auth`), avec une seule porte : la table `user` vide, pour amorcer une installation. Chaque inscription crée l'**espace personnel** de l'utilisateur (`create.after`) — sans lui, un invité serait bloqué par `orgProcedure` entre son inscription et l'acceptation de l'invitation. `settings.save` passe par `adminProcedure` (`user.is_admin`, posé à la main en base) : elle écrase la clé privée Enable Banking de toute l'installation.
- **`/espaces`** (portage de `Espaces.dc.html`, maquette du 2026-08-05) est le quatrième écran de réglages : une carte par espace (compteurs, membres, invitations, bandeau de consentement bancaire), plus l'écran public **`/invitation/$invitationId`**. Le changement d'espace **recharge le document** — le périmètre n'étant pas dans l'URL, react-query servirait sinon le cache de l'espace quitté ; la bascule reste aussi dans le menu de l'engrenage, à partir de deux espaces.
  - **`organization.is_personal` est une colonne, pas une déduction.** Un espace partagé dont on n'a encore invité personne est indiscernable d'un espace personnel par son nombre de membres, alors qu'il ne se comporte pas pareil : le personnel ne se supprime pas (il naît et meurt avec le compte) et se _convertit_, le partagé se supprime et se quitte.
  - **La conversion est la réponse au seul vrai trou du parcours** : rien ne déplace un compte d'un espace à un autre, donc quand on veut partager un budget déjà constitué, c'est l'espace lui-même qui s'ouvre (`spaces.share` : renomme + `is_personal = false`, rien d'autre ne bouge). Le dialogue de création propose les deux chemins et dit ce que chacun coûte ; l'espace neuf est vide et l'annonce. Sans retour arrière : le hook d'inscription ne s'exécute qu'une fois, rien ne recrée un espace personnel.
  - **`spacesRouter` n'utilise pas `orgProcedure`** — c'est le seul routeur qui parle _des_ espaces au lieu de travailler _dans_ un espace. Chaque procédure porte donc sa propre autorisation sur l'espace que l'input désigne (`assertOwner` / `assertMember`), et `spaces.invitation` est carrément **publique** : l'écran d'acceptation doit s'afficher pour quelqu'un qui n'a pas encore de compte. Elle ne renvoie que nom de l'espace, invitant et volumétrie — jamais les membres.
  - **Les mutations écrivent les tables du plugin directement** (Drizzle), sans passer par les endpoints better-auth : tout le reste de l'app parle à la base par tRPC, et remettre l'API auth dans le contexte casse le build de déclarations. Seul `setActive` reste côté client, puisqu'il touche la session.
  - **`expired` n'est pas un statut stocké** : la table ne connaît que pending/accepted/canceled/rejected et une invitation périmée y reste « pending ». Il est dérivé de `expires_at` à la lecture — une ligne dont l'échéance est passée ne vaut plus rien, quelle que soit sa colonne, et ça évite un job de nettoyage.
  - **Deux gardes sur « Quitter »**, pour deux impasses différentes : le dernier propriétaire laisserait un espace que personne ne peut plus administrer, et son dernier espace laisserait l'utilisateur sans espace actif, donc devant un `FORBIDDEN` sur chaque écran.
  - L'envoi d'email est **minimal et volontairement pauvre** (`lib/email.ts`, POST à Resend, aucune dépendance) : sans `RESEND_API_KEY`/`EMAIL_FROM`, le lien part dans les logs serveur plutôt que d'être perdu, et l'échec d'envoi n'annule jamais l'invitation créée (elle reste renvoyable). Pas de suivi de délivrabilité — « envoyée » et « acceptée » sont des faits, « reçue » n'en serait pas un.
- **`ctx.authApi` a été retiré du contexte tRPC** : aucune procédure ne s'en servait, et depuis le plugin `organization` son type est assez gros pour que `tsc` renonce à sérialiser celui d'`appRouter` (« inferred type … exceeds the maximum length »), ce qui casse le build de déclarations de `@budget/api`. Ne pas le remettre.

## Commands

- `pnpm dev` — turbo watch dev (tous les packages/apps en mode dev).
- `pnpm -F @budget/tanstack-start dev` — web app seule, http://localhost:3000 (port aligné sur l'URL de callback Enable Banking `http://localhost:3000/callback`).
- `docker compose up -d` — Postgres 17 local (port hôte 5436). **Instance partagée avec l'ancien repo `budget-tracker`** (même conteneur, même volume).
- `pnpm db:push` — push du schéma Drizzle (turbo task interactive) ; **échoue dans un environnement non-TTY**. Fallback : `pnpm -F @budget/db with-env drizzle-kit push`.
- `pnpm test` — turbo run test (Vitest sur tous les packages).
- `pnpm build` / `pnpm typecheck` / `pnpm lint` — turbo run sur tout le monorepo.

**Il n'existe plus de commande CLI métier** (`import`, `categorize`, `suggest-categories`, `sync` ont été supprimées) : tout se déclenche depuis la webapp, via les mutations tRPC correspondantes.

- `sync.run` (bouton Synchroniser) — pipeline complet Enable Banking → import → catégorisation. **Never trigger `sync.run` on behalf of the user** : il touche aux sessions bancaires réelles et déclenche une SCA. L'autorisation bancaire se fait sur la page `/banques`.
- `sync.import` — rejoue l'import des `data/*.json` déjà présents puis la catégorisation, **sans aucun appel bancaire** (ni SCA, ni consommation du quota PSD2). C'est le remplaçant de l'ancien `pnpm run import` ; idempotent, safe à relancer.
- `categories.categorize` — catégorisation LLM des transactions sans catégorie (idempotent, garde `IS NULL`). Une transaction qu'aucune catégorie existante ne décrit reste volontairement sans catégorie et sera resoumise au run suivant : un `remaining` qui ne bouge pas signale une branche manquante dans l'arborescence, pas un bug — lancer l'analyse de suggestions depuis `/categories`.
- `categories.suggestions.generate` — analyse LLM proposant une arborescence ; n'écrit **rien** en base (ni `accept`, ni `apply` ne sont appelés pour elle). Sûr à relancer.
- `categories.suggestions.accept` — accepte **une** branche proposée : crée la catégorie manquante et range ses transactions encore sans catégorie, sans passe LLM. C'est ce que fait chaque bouton « Ajouter » de `/categories`.

## Base de données — ne jamais confondre avec l'ancien repo

La base de ce projet est **`budget_t3`** (instance Docker **partagée** avec `budget-tracker`, port hôte 5436). Ne JAMAIS lancer un push (`db:push` / `drizzle-kit push`) ou toute commande destructive avec une `POSTGRES_URL` pointant sur la base `budget` (celle de l'ancien repo) — vérifier systématiquement le nom de la base dans `POSTGRES_URL`/`.env` avant toute opération de schéma.

### Seed initial de la table `categories`

Sur un clone neuf, la table `categories` est vide tant qu'elle n'a pas été seedée — la catégorisation fonctionne quand même (no-op silencieux, les transactions restent sans catégorie). Seeder avant la première catégorisation :

```sql
INSERT INTO categories (name, color) VALUES
  ('Revenus', '#00c65a'), ('Logement', '#1447e6'), ('Alimentation', '#b55200'),
  ('Restaurants & bars', '#007857'), ('Transport', '#0084c8'), ('Santé', '#fb64b6'),
  ('Abonnements', '#83cc00'), ('Loisirs & shopping', '#8d56ff'),
  ('Épargne & virements internes', '#fb2c36'), ('Frais & impôts', '#9810fa'), ('Autres', '#94a3b8')
ON CONFLICT (name) DO NOTHING;
```

Ce seed n'est qu'un point de départ : aucun de ces noms n'est référencé par le code (le prompt de catégorisation lit la table, voir Architecture). L'arborescence est censée diverger de cette liste au fil des suggestions appliquées depuis `/categories`.

### Extension `pg_trgm` (catégorisation few-shot)

La recherche de transactions similaires (`categorization/similar.ts`) utilise `similarity()` sur la description, fourni par l'extension PostgreSQL `pg_trgm`. Activée automatiquement sur un volume Docker neuf via `docker-initdb/01-pg_trgm.sql` (monté dans `/docker-entrypoint-initdb.d`, ne s'exécute qu'à la création initiale du volume — voir `docker-compose.yml`).

Sur une instance déjà initialisée avant ce script (ex. le volume partagé avec `budget-tracker`), l'activer manuellement une fois (survit à `db:push`, pas géré par Drizzle) :

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

## Bank data provider: Enable Banking (not GoCardless)

This was a deliberate decision after research, not an assumption — do not revert to GoCardless without re-checking the facts below.

**Why not GoCardless (ex-Nordigen):** confirmed directly on `bankaccountdata.gocardless.com/new-signups-disabled` that GoCardless Bank Account Data is **closed to new signups** — a new project cannot get credentials for it. (If a `secret_id`/`secret_key` from before the shutdown ever surfaces, it might still work, but that can't be relied on for new setup instructions.)

**Chosen alternative: [Enable Banking](https://enablebanking.com).** Verified reasons it fits this project specifically:

- Self-serve signup (just an email — no company/SIRET required to create an account).
- Its **Restricted Production** mode is free, uses real bank data, and its terms explicitly permit _"the personal use of private individuals"_ — this project's exact use case (own accounts, non-commercial). In this mode only accounts you personally link are accessible.
- 2700+ banks across 30 European countries.
- It's the option the wider open-source personal-finance community converged on post-GoCardless-shutdown (e.g. the "Enable Actual" community integration for Actual Budget).
- Trade-off to keep in mind: among mainstream providers, it is close to the _only_ one offering free self-serve access for individuals — Powens, Bridge/Bankin, Tink, Yapily are B2B/sales-led only; Plaid's free tier is US/Canada-only. That's a single-vendor dependency risk (the same kind of risk that just killed the GoCardless setup), acceptable for a hobby project but worth remembering if this ever needs a second provider.
- Regulatory note independent of provider: PSD2 consent must be renewed periodically (~180 days for most EEA ASPSPs) — periodic sync will never be fully unattended long-term; expect to re-authenticate roughly twice a year regardless of provider.
