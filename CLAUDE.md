# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A personal finance tool (in French — user-facing strings, comments, and category names should be in French) for syncing transactions from 3 personal bank accounts, categorizing them, and generating budget/savings reports.

This is a pnpm + Turborepo monorepo (migrated from the single-package `budget-tracker` CLI tool). It reuses the same business pipeline (Enable Banking → import → categorize → PostgreSQL → transactions table) but split across workspace packages and apps.

## Architecture

- `@budget/db` — schéma Drizzle + `pg`, base **`budget_t3`**. Le cloisonnement par espace est décrit dans « Espaces (multi-utilisateurs) » plus bas.
- `@budget/api` — routeurs tRPC (`router/`) + domaines `banking/`, `transactions/`, `categorization/`, `categories/`, `pipeline.ts`. **Détail et fournisseur bancaire (Enable Banking) : `packages/api/CLAUDE.md`**, chargé quand tu travailles sous `packages/api/`.

- `@budget/auth` — Better Auth, email/mot de passe + plugin `organization` (voir « Espaces » plus haut).
- `@budget/ui` — composants Base UI. Déviation assumée par rapport au template create-t3-turbo : le `ThemeProvider` maison a été conservé (pas `next-themes`), `ThemeToggle` réécrit sans dropdown.
- `@budget/shared` — code partagé api↔apps sans dépendance lourde (`src/schemas.ts` : schéma Zod + `PAGE_SIZE` ; `src/colors.ts` : palette de catégories ; `src/icons.ts` : jeu d'icônes de catégories, **noms et mots-clés seulement**). Sa seule dépendance runtime est `zod`, et **c'est la raison d'être du package** : `transactionsSearchSchema` est consommé comme valeur au runtime dans le navigateur (`validateSearch` d'une route TanStack) autant que par l'input tRPC. Le mettre dans `@budget/api` ferait entrer `@budget/db`/`pg`, le SDK Anthropic et better-auth dans le bundle client — tous les autres imports app → `@budget/api` sont des `import type`, effacés à la compilation. Ne jamais y ajouter de dépendance lourde.
- `apps/tanstack-start` — app web : `/login`, `/callback`, `/banques`, `/categories`, `/espaces`, et la revue du mois sous le layout `_authed/_revue` (`/` l'anneau, `/transactions` la table). **Détail (maquettes, design system, revue, anneau) : `apps/tanstack-start/CLAUDE.md`**, chargé quand tu travailles sous `apps/tanstack-start/`.
  - Une règle du design system dépasse l'app et reste ici, parce qu'elle vise un fichier de `packages/ui` : l'échelle typographique est fermée à 9 crans nommés par rôle, déclarés dans `src/styles.css`.
    - **Un cran ajouté doit l'être à deux endroits** : `styles.css` _et_ la liste `font-size` de `extendTailwindMerge` dans `packages/ui/src/index.ts`. Le groupe `text-color` de `tailwind-merge` accepte n'importe quel mot après `text-` : sans la déclaration, il range `text-hero` parmi les couleurs et le **supprime** dès qu'une couleur suit dans le même `cn()`. La panne est silencieuse et générale — `cn("num text-hero", "text-bad")` ne rend que `text-bad`, le CSS émis reste parfaitement correct, et c'est tout le bandeau qui retombe à la taille héritée. `packages/ui/src/index.test.ts` la verrouille ; ne pas la supprimer.

### App mobile — supprimée le 2026-08-07

`apps/expo` (gluestack-ui v5 + nativewind) était **en suspens depuis le 2026-07-23** : l'objectif restait une vraie app universelle web+native, ce que gluestack ne permet pas correctement. Deux semaines plus tard elle n'avait toujours pas repris, et 5 600 lignes gelées plus 52 dépendances pesaient sur chaque `pnpm install`, chaque `turbo run` et chaque relecture — elle a été supprimée, avec `tooling/tailwind` dont elle était le seul consommateur. `git log` la rend : partir de là plutôt que de la réécrire, mais **sans reprendre gluestack**, qui est la raison du gel.

Deux traces subsistent volontairement, sans consommateur aujourd'hui : le CORS + `trustedOrigins` better-auth ouverts à `localhost:*` en dev (`apps/tanstack-start/src/lib/cors.ts`, `src/auth/server.ts`) et le `host: true` du `vite.config.ts`, qui laissaient le téléphone atteindre l'API en LAN. Inoffensifs en dev, et exactement ce qu'il faudrait remettre.

Pipeline métier inchangé : connexions bancaires configurées dans l'app (`/banques` : onboarding Enable Banking, wizard d'ajout, callback OAuth sur `/callback`, sessions stockées en DB) → sync → `data/<orgId>/*.json` (racine du monorepo, un répertoire par espace) → import (`packages/api/src/transactions/import.ts`) → PostgreSQL → tRPC (`@budget/api` routers) → table des transactions (`apps/tanstack-start`).

## Espaces (multi-utilisateurs) — cloisonnement

L'app est multi-utilisateurs depuis le 2026-08-05. L'unité de cloisonnement est l'**espace** : un utilisateur seul, ou un foyer partagé. Un espace **est** une `organization` du plugin `organization` de better-auth — pas de table maison : le plugin apporte `organization` / `member` / `invitation`, les rôles, le flux d'invitation, et surtout `session.active_organization_id`, ce qui fait vivre l'espace courant **dans la session et non dans l'URL**. C'est pour ça qu'aucune route n'a de segment d'espace et que le portage n'a touché aucun loader.

- **Ce qui porte un `organization_id`** : `bank_connections`, `auth_requests`, `bank_accounts`, `categories`. Pas `transactions` — leur espace se lit par leur compte, et presque toutes les requêtes joignaient déjà `bank_accounts`. Ne pas dénormaliser : ce serait une seconde vérité pouvant diverger du compte. Pas `category_budgets` non plus (via sa catégorie). Pas `app_settings`, qui est la configuration Enable Banking de l'**installation** — une par déploiement, pas une par foyer.
- **Les catégories appartiennent à l'espace, jamais au compte bancaire.** Toute l'app agrège _par catégorie, à travers les comptes_ : le compte est un périmètre de lecture. Et **un compte appartient à exactement un espace** — partager un compte = ajouter un membre à l'espace. C'est ce qui permet à `transactions.category_id` de rester une seule colonne ; une table `transaction_categories` par espace multiplierait chaque agrégat et chaque passe LLM par le nombre d'espaces. À ne pas rouvrir sans décision explicite.
- **`categories.name` n'est unique que dans l'espace** (`UNIQUE(organization_id, name)`), idem `accounts.uid` — deux membres d'un couple qui connectent chacun le même compte joint peuvent recevoir le même uid d'Enable Banking, une unicité globale ferait échouer le second sans rien expliquer. Tout ce qui résout une catégorie par son nom (`upsertCategory`, `setTransactionCategory`, le filtre `category` de l'URL, l'`onConflict` de `apply.ts`) doit porter l'espace.
- **Le point de passage est `orgProcedure`** (`packages/api/src/trpc.ts`) : elle lit `session.activeOrganizationId` — **jamais un input** — et revérifie l'appartenance à chaque requête, pour qu'une exclusion prenne effet sans attendre l'expiration de la session. Chaque service reçoit l'`organizationId` en **premier paramètre**. Côté transactions, le filtre commun `transactionsFilterQuery(organizationId, query)` pose la condition avant tout filtre d'URL ; deux requêtes ne passent pas par lui et ont dû recevoir leur `innerJoin(accounts)` : le décompte de `categorization/run.ts` et les cinq requêtes de `categorization/similar.ts` — sans quoi le few-shot injecterait les transactions d'un autre foyer comme exemples dans le prompt (fuite _et_ dégradation).
- **Les mutations par id sont des IDOR en puissance** : tout id venant du client (`setTransactionCategory`, `removeCategory`, `setCategoryBudget`, `revokeConnection`, `acceptSuggestion`…) porte l'espace dans son `WHERE`, et pour les écritures sur `transactions` c'est `ownedByOrganization()` (`EXISTS` corrélé — un `UPDATE` n'a pas de `FROM bank_accounts`). Attention au **succès silencieux** : un `UPDATE` qui ne touche aucune ligne ne lève rien, d'où la vérification explicite en amont là où l'UI attend une confirmation (`renameCategory`).
- **Les états hors base sont scopés eux aussi**, et c'est le genre de fuite qu'aucun `WHERE` ne rattrape : les verrous `single-flight` valent `sync:${orgId}` / `categorize:${orgId}`, et les JSON Enable Banking vivent dans `data/<orgId>/`. Le troisième — l'état des suggestions — a été supprimé plutôt que scopé : il vit maintenant côté navigateur (voir « Suggestions » plus haut). Ce dernier point n'est pas du rangement : `importTransactions` lit _tout_ le répertoire qu'on lui donne — à plat, un import déclenché par un espace avalerait les fichiers d'un autre et le verrou par espace deviendrait un mensonge.
- **Inscription ouverte** depuis le 2026-08-08 : n'importe qui peut créer un compte depuis `/login` (le hook `user.create.before` qui exigeait une invitation en attente — ou une table `user` vide pour amorcer — a été supprimé). Une invitation ne donne donc plus le droit d'exister, seulement l'adhésion à un espace partagé, et `/invitation/$invitationId` n'a pas bougé. Chaque inscription crée l'**espace personnel** de l'utilisateur (`create.after`), nommé d'après le nom donné ou le préfixe de l'adresse, renommable sur `/espaces`
  - **Connexion par lien email uniquement** (plugin `magicLink`, `@budget/auth`), depuis le 2026-08-08 : il n'y a **plus de mot de passe du tout** — `emailAndPassword` est absent de la config, et les hachages des comptes antérieurs dorment dans `account` sans appelant. Un même geste connecte, inscrit si l'adresse est inconnue (`disableSignUp` laissé à `false`) et **prouve l'adresse**. Cette troisième propriété n'est pas un effet de bord : elle est la contrepartie exacte de `spaces.incoming`, où l'on verrait sinon les invitations d'une adresse qu'il suffirait de déclarer. Elle a d'abord été tenue par `requireEmailVerification` + `emailVerification` (matinée du 2026-08-08), supprimés avec les mots de passe parce que le lien les rend redondants — **ne pas remettre un chemin par mot de passe sans rétablir en même temps une preuve d'adresse**, ce serait rouvrir ce trou-là. `expiresIn` vaut 15 minutes (5 par défaut, trop court pour un aller-retour sur téléphone) et la valeur est annoncée dans l'email et sur les deux écrans : `MAGIC_LINK_MINUTES` est la seule source. `/login` n'a plus qu'un champ, et `/invitation/$invitationId` demande un lien avec son `callbackURL` au lieu d'enchaîner sur `acceptInvitation`, qui n'aurait pas de session — le champ « Votre nom » y reste, lui, parce que les autres membres de l'espace le liront dans la liste — sans lui, un invité serait bloqué par `orgProcedure` entre son inscription et l'acceptation de l'invitation. `settings.save` passe par `adminProcedure` (`user.is_admin`, posé à la main en base) : elle écrase la clé privée Enable Banking de toute l'installation.
- **`/espaces`** (portage de `Espaces.dc.html`, maquette du 2026-08-05) est le troisième écran de réglages : une carte par espace (compteurs, membres, invitations, bandeau de consentement bancaire), plus l'écran public **`/invitation/$invitationId`**. Le changement d'espace **recharge le document** — le périmètre n'étant pas dans l'URL, react-query servirait sinon le cache de l'espace quitté ; la bascule reste aussi dans le menu de l'engrenage, à partir de deux espaces.
  - **`organization.is_personal` est une colonne, pas une déduction.** Un espace partagé dont on n'a encore invité personne est indiscernable d'un espace personnel par son nombre de membres, alors qu'il ne se comporte pas pareil : le personnel ne se supprime pas (il naît et meurt avec le compte) et se _convertit_, le partagé se supprime et se quitte.
  - **La conversion est la réponse au seul vrai trou du parcours** : rien ne déplace un compte d'un espace à un autre, donc quand on veut partager un budget déjà constitué, c'est l'espace lui-même qui s'ouvre (`spaces.share` : renomme + `is_personal = false`, rien d'autre ne bouge). Le dialogue de création propose les deux chemins et dit ce que chacun coûte ; l'espace neuf est vide et l'annonce. Sans retour arrière : le hook d'inscription ne s'exécute qu'une fois, rien ne recrée un espace personnel.
  - **`spaces.incoming` est le pendant de l'inscription ouverte** : les invitations en attente adressées à l'email de la session, en bandeau en haut de `/espaces` avec « Rejoindre » / « Refuser ». Sans elle, le lien reçu par email serait la seule porte d'un espace partagé — or on peut désormais créer son compte sans jamais le cliquer, et un email perdu enfermerait la personne dans son espace personnel. Les périmées sont écartées par la requête et non rendues avec un statut : `expires_at` étant dérivé à la lecture (voir plus bas), une invitation qu'on ne peut plus accepter n'a rien à faire dans une liste de gestes à faire. Scopée par `ctx.session.user.email`, jamais par un input — même critère que celui qu'`acceptInvitation` revérifie.
  - **`spacesRouter` n'utilise pas `orgProcedure`** — c'est le seul routeur qui parle _des_ espaces au lieu de travailler _dans_ un espace. Chaque procédure porte donc sa propre autorisation sur l'espace que l'input désigne (`assertOwner` / `assertMember`), et `spaces.invitation` est carrément **publique** : l'écran d'acceptation doit s'afficher pour quelqu'un qui n'a pas encore de compte. Elle ne renvoie que nom de l'espace, invitant et volumétrie — jamais les membres.
  - **Les mutations écrivent les tables du plugin directement** (Drizzle), sans passer par les endpoints better-auth : tout le reste de l'app parle à la base par tRPC, et remettre l'API auth dans le contexte casse le build de déclarations. Seul `setActive` reste côté client, puisqu'il touche la session.
  - **`expired` n'est pas un statut stocké** : la table ne connaît que pending/accepted/canceled/rejected et une invitation périmée y reste « pending ». Il est dérivé de `expires_at` à la lecture — une ligne dont l'échéance est passée ne vaut plus rien, quelle que soit sa colonne, et ça évite un job de nettoyage.
  - **Deux gardes sur « Quitter »**, pour deux impasses différentes : le dernier propriétaire laisserait un espace que personne ne peut plus administrer, et son dernier espace laisserait l'utilisateur sans espace actif, donc devant un `FORBIDDEN` sur chaque écran.
  - L'envoi d'email est **minimal et volontairement pauvre** (`packages/auth/src/email.ts`, POST à Resend, aucune dépendance) : deux messages, le lien de connexion et l'invitation. Le module vit dans `@budget/auth` et non dans `@budget/api` parce que better-auth déclenche lui-même le lien de connexion : la dépendance va api → auth, l'inverse serait un cycle. **`send()` a deux régimes selon `NODE_ENV`, et c'est la connexion par lien qui l'impose** : l'email n'est plus un confort, c'est l'unique authentification, sans repli par mot de passe. En développement une clé absente écrit le lien dans les logs — c'est ce qui permet de travailler sans domaine d'envoi ; **en production elle lève**, pour que l'écran de connexion ne puisse pas annoncer un email que personne n'a envoyé. Une erreur d'envoi Resend remontait déjà ; une clé manquante, non — cette asymétrie était sans conséquence pour les invitations, elle rendrait l'app inaccessible en silence pour la connexion. L'échec n'annule jamais l'invitation créée (elle reste renvoyable). Pas de suivi de délivrabilité — « envoyée » et « acceptée » sont des faits, « reçue » n'en serait pas un.
- **`ctx.authApi` a été retiré du contexte tRPC** : aucune procédure ne s'en servait, et depuis le plugin `organization` son type est assez gros pour que `tsc` renonce à sérialiser celui d'`appRouter` (« inferred type … exceeds the maximum length »), ce qui casse le build de déclarations de `@budget/api`. Ne pas le remettre.

## Commands

- `pnpm -F @budget/tanstack-start dev` — web app seule, http://localhost:3000 (port aligné sur l'URL de callback Enable Banking `http://localhost:3000/callback`).
- `docker compose up -d` — Postgres 17 local (port hôte 5436). **Instance partagée avec l'ancien repo `budget-tracker`** (même conteneur, même volume).
- `pnpm db:generate` — écrit le SQL du changement de schéma dans `packages/db/drizzle/` (à relire et à committer avec le changement de `schema.ts`), puis `pnpm db:migrate` l'applique. **`push` a été supprimé le 2026-08-12** : il modifiait la base sans laisser de fichier, donc sans rien à rejouer au déploiement — la prod n'a pas de TTY et sa base ne publie aucun port. Voir « Migrations » plus bas.

**Il n'existe plus de commande CLI métier** (`import`, `categorize`, `suggest-categories`, `sync` ont été supprimées) : tout se déclenche depuis la webapp, via les mutations tRPC correspondantes.

- `sync.run` (bouton Synchroniser) — pipeline complet Enable Banking → import → catégorisation. **Never trigger `sync.run` on behalf of the user** : il touche aux sessions bancaires réelles et déclenche une SCA. L'autorisation bancaire se fait sur la page `/banques`.
- `sync.import` — rejoue l'import des `data/*.json` déjà présents puis la catégorisation, **sans aucun appel bancaire** (ni SCA, ni consommation du quota PSD2). C'est le remplaçant de l'ancien `pnpm run import` ; idempotent, safe à relancer.
- `categories.categorize` — catégorisation LLM des transactions sans catégorie (idempotent, garde `IS NULL`). Une transaction qu'aucune catégorie existante ne décrit reste volontairement sans catégorie et sera resoumise au run suivant : un `remaining` qui ne bouge pas signale une branche manquante dans l'arborescence, pas un bug — lancer l'analyse de suggestions depuis `/categories`.
- `categories.suggestions.generate` — analyse LLM proposant une arborescence ; n'écrit **rien** en base (ni `accept`, ni `apply` ne sont appelés pour elle). Sûr à relancer.
- `categories.suggestions.accept` — accepte **une** branche proposée : crée la catégorie manquante et range ses transactions encore sans catégorie, sans passe LLM. C'est ce que fait chaque bouton « Ajouter » de `/categories`.

## Base de données — ne jamais confondre avec l'ancien repo

La base de ce projet est **`budget_t3`** (instance Docker **partagée** avec `budget-tracker`, port hôte 5436). Ne JAMAIS lancer une migration (`db:migrate` / `drizzle-kit migrate`) ou toute commande destructive avec une `POSTGRES_URL` pointant sur la base `budget` (celle de l'ancien repo) — vérifier systématiquement le nom de la base dans `POSTGRES_URL`/`.env` avant toute opération de schéma.

### Migrations versionnées (depuis le 2026-08-12)

`packages/db/drizzle/` : un `.sql` par changement, plus `meta/_journal.json`. `pnpm db:generate` écrit le fichier, `pnpm db:migrate` l'applique, et `deploy/deploy.sh` rejoue le même SQL sur la prod **avant** de démarrer le code neuf (schéma neuf + code ancien est inoffensif, l'inverse lève sur chaque écran). La base de prod ne publiant aucun port, le script y accède par un tunnel SSH vers l'IP de bridge du conteneur, le temps du `migrate`.

- **`0000_baseline.sql` décrit le schéma tel qu'il tournait déjà** : il n'a jamais été exécuté nulle part. Les bases existantes ont été « baselinées » — une ligne dans `drizzle.__drizzle_migrations` qui dit « je suis au niveau du socle ». La procédure pour la prod est en tête de `deploy/deploy.sh` ; sans elle, le premier `migrate` rejoue les `CREATE TABLE` et échoue.
- **Le migrateur ne compare que `created_at` au `when` du journal, jamais le hash** (`drizzle-orm/pg-core/dialect.js`) : une migration est « déjà appliquée » si sa date est antérieure à la dernière enregistrée. Éditer un `.sql` déjà appliqué ne le rejoue donc pas — il faut en générer un nouveau.
  - Corollaire, et c'est le piège que `push` n'avait pas : une migration dont le `when` est **antérieur** à la dernière appliquée est ignorée **en silence**, sans erreur ni trace. `db:generate` horodate à l'heure de génération, donc deux branches qui en produisent chacune une, fusionnées dans l'autre ordre, en perdent une. Générer dans l'ordre où ça s'appliquera ; après un rebase qui réordonne des migrations, regénérer plutôt que réordonner les fichiers.
- `pnpm db:migrate` reste **relançable** : sans rien à faire, il ne fait rien.

### Seed initial et extension `pg_trgm`

Sur un clone neuf : seeder la table `categories` avant la première catégorisation, et activer `pg_trgm` (nécessaire au few-shot). Le SQL des deux est dans **`packages/db/CLAUDE.md`**.
