# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A personal finance tool (in French — user-facing strings, comments, and category names should be in French) for syncing transactions from 3 personal bank accounts, categorizing them, and generating budget/savings reports.

This is a pnpm + Turborepo monorepo (migrated from the single-package `budget-tracker` CLI tool). It reuses the same business pipeline (Enable Banking → import → categorize → PostgreSQL → transactions table) but split across workspace packages and apps.

## Architecture

- `@budget/db` — schéma Drizzle + `pg`, base **`budget_t3`**. Le cloisonnement par espace est décrit dans « Espaces (multi-utilisateurs) » plus bas. **Seed d'un clone neuf et extension `pg_trgm` : `packages/db/CLAUDE.md`.**
- `@budget/api` — routeurs tRPC (`router/`) + domaines `banking/`, `transactions/`, `categorization/`, `categories/`, `spaces/`, `pipeline.ts`. **Détail et fournisseur bancaire (Enable Banking) : `packages/api/CLAUDE.md`**, chargé quand tu travailles sous `packages/api/`.
  - **Deux points d'entrée, et la différence est le bundle client.** `@budget/api` (racine) exporte `appRouter` et des types — côté app, ne l'importer qu'en `import type`. `@budget/api/schemas` (sous-chemin, `src/schemas.ts`) n'exporte que du Zod et des constantes (`transactionsSearchSchema`, `PAGE_SIZE`, `categoryOverviewSchema`, `NO_CATEGORY_NAME`…) : c'est lui que le navigateur importe **comme valeur** (`validateSearch` des routes). Un import de valeur depuis la racine ferait entrer `@budget/db`/`pg`, le SDK Anthropic et better-auth dans le bundle client. Ces schémas vivaient dans `@budget/shared` jusqu'au 2026-08-22.
- `@budget/auth` — Better Auth, lien magique + plugin `organization` (voir « Espaces » plus bas).
- `@budget/ui` — composants Base UI (`button`, `dialog`, `toolbar`…) et, sous `src/three/`, les primitives de l'anneau 3D (`CanvasContainer`, `Segment`, `SegmentLabel`, `SegmentDetail`, `tuning.ts`) — react-three-fiber, drei, postprocessing, leva. Déviation assumée par rapport au template create-t3-turbo : le `ThemeProvider` maison a été conservé (pas `next-themes`). **Le design appartient à ce package** : `docs/adr/0001-le-design-appartient-au-package-ui.md`.
- `@budget/shared` — `src/colors.ts` (palette de catégories) et `src/icons.ts` (jeu d'icônes de catégories, **noms et mots-clés seulement**). Sa seule dépendance runtime est `zod` ; il est consommé par l'api comme par l'app. Ne jamais y ajouter de dépendance lourde ni de composant (`lucide-react` y ferait entrer ~1500 icônes).
- `apps/tanstack-start` — app web : `/login`, `/invitation/$invitationId`, `/callback`, les réglages sous `/settings/{banques,categories,espaces}`, et la revue du mois sous le layout `_authed/_period-overview` (`/` l'anneau, `/transactions` la table). **Détail (maquettes, design system, revue, anneau) : `apps/tanstack-start/CLAUDE.md`**, chargé quand tu travailles sous `apps/tanstack-start/`.
  - Une règle du design system dépasse l'app et reste ici, parce qu'elle vise un fichier de `packages/ui` : l'échelle typographique est fermée à 9 crans nommés par rôle, déclarés dans `src/styles.css`.
    - **Un cran ajouté doit l'être à deux endroits** : `styles.css` _et_ la liste `font-size` de `extendTailwindMerge` dans `packages/ui/src/index.ts`. Le groupe `text-color` de `tailwind-merge` accepte n'importe quel mot après `text-` : sans la déclaration, il range `text-hero` parmi les couleurs et le **supprime** dès qu'une couleur suit dans le même `cn()`. La panne est silencieuse et générale — `cn("num text-hero", "text-bad")` ne rend que `text-bad`, le CSS émis reste parfaitement correct, et c'est tout le bandeau qui retombe à la taille héritée. `packages/ui/src/index.test.ts` la verrouille ; ne pas la supprimer.

### App mobile — supprimée le 2026-08-07

`apps/expo` (gluestack-ui v5 + nativewind) était en suspens depuis le 2026-07-23 : l'objectif restait une vraie app universelle web+native, ce que gluestack ne permet pas correctement. Elle a été supprimée avec `tooling/tailwind`. `git log` la rend : partir de là plutôt que de la réécrire, mais **sans reprendre gluestack**, qui est la raison du gel.

Deux traces subsistent volontairement, sans consommateur aujourd'hui : le CORS + `trustedOrigins` better-auth ouverts à `localhost:*` en dev (`apps/tanstack-start/src/lib/cors.ts`, `src/auth/server.ts`) et le `host: true` du `vite.config.ts`, qui laissaient le téléphone atteindre l'API en LAN. Inoffensifs en dev, et exactement ce qu'il faudrait remettre.

Pipeline métier inchangé : connexions bancaires configurées dans l'app (`/settings/banques` : onboarding Enable Banking, wizard d'ajout, callback OAuth sur `/callback`, sessions stockées en DB) → sync → `data/<orgId>/*.json` (racine du monorepo, un répertoire par espace) → import (`packages/api/src/transactions/import.ts`) → PostgreSQL → tRPC (`@budget/api` routers) → revue et table des transactions (`apps/tanstack-start`).

## Espaces (multi-utilisateurs) — cloisonnement

L'app est multi-utilisateurs depuis le 2026-08-05. L'unité de cloisonnement est l'**espace** : un utilisateur seul, ou un foyer partagé. Un espace **est** une `organization` du plugin `organization` de better-auth — pas de table maison : le plugin apporte `organization` / `member` / `invitation`, les rôles, le flux d'invitation, et surtout `session.active_organization_id`, ce qui fait vivre l'espace courant **dans la session et non dans l'URL**. C'est pour ça qu'aucune route n'a de segment d'espace et que le portage n'a touché aucun loader.

- **Ce qui porte un `organization_id`** : `bank_connections`, `auth_requests`, `bank_accounts`, `categories`. Pas `transactions` — leur espace se lit par leur compte, et presque toutes les requêtes joignaient déjà `bank_accounts`. Ne pas dénormaliser : ce serait une seconde vérité pouvant diverger du compte. Pas `app_settings`, qui est la configuration Enable Banking de l'**installation** — une par déploiement, pas une par foyer.
- **Les catégories appartiennent à l'espace, jamais au compte bancaire.** Toute l'app agrège _par catégorie, à travers les comptes_ : le compte est un périmètre de lecture. Et **un compte appartient à exactement un espace** — partager un compte = ajouter un membre à l'espace. C'est ce qui permet à `transactions.category_id` de rester une seule colonne ; une table `transaction_categories` par espace multiplierait chaque agrégat et chaque passe LLM par le nombre d'espaces. À ne pas rouvrir sans décision explicite.
- **`categories.name` n'est unique que dans l'espace** (`UNIQUE(organization_id, name)`), idem `bank_accounts.uid` — deux membres d'un couple qui connectent chacun le même compte joint peuvent recevoir le même uid d'Enable Banking, une unicité globale ferait échouer le second sans rien expliquer. Tout ce qui résout une catégorie par son nom (le filtre `category` de l'URL, `createCategory`/`renameCategory`) doit porter l'espace.
- **Le point de passage est `orgProcedure`** (`packages/api/src/trpc.ts`) : elle lit `session.activeOrganizationId` — **jamais un input** — et revérifie l'appartenance à chaque requête, pour qu'une exclusion prenne effet sans attendre l'expiration de la session. Chaque service reçoit l'`organizationId` en **premier paramètre**. Côté transactions, le filtre commun `transactionsFilterQuery(organizationId, query)` pose la condition avant tout filtre d'URL ; les requêtes qui ne passent pas par lui portent leur propre condition sur `bank_accounts.organization_id` : le CTE `filterTransactions` (agrégats), le décompte de `categorization/run.ts` et les requêtes de `categorization/similar.ts` — sans quoi le few-shot injecterait les transactions d'un autre foyer comme exemples dans le prompt (fuite _et_ dégradation).
- **Les mutations par id sont des IDOR en puissance** : tout id venant du client (`updateCategory`, `setExcluded`, `categories.remove`, `budgets.set`, `revokeConnection`…) porte l'espace dans son `WHERE`, et pour les écritures sur `transactions` c'est `ownedByOrganization()` (`EXISTS` corrélé — un `UPDATE` n'a pas de `FROM bank_accounts`). Attention au **succès silencieux** : un `UPDATE` qui ne touche aucune ligne ne lève rien, d'où le `returning` + erreur explicite là où l'UI attend une confirmation (`renameCategory`, `setCategoryBudget`).
- **Les états hors base sont scopés eux aussi**, et c'est le genre de fuite qu'aucun `WHERE` ne rattrape : les verrous `single-flight` valent `sync:${orgId}` / `categorize:${orgId}`, et les JSON Enable Banking vivent dans `data/<orgId>/`. Ce dernier point n'est pas du rangement : `importTransactions` lit _tout_ le répertoire qu'on lui donne — à plat, un import déclenché par un espace avalerait les fichiers d'un autre et le verrou par espace deviendrait un mensonge.
- **Inscription ouverte** depuis le 2026-08-08 : n'importe qui peut créer un compte depuis `/login`. Une invitation ne donne donc pas le droit d'exister, seulement l'adhésion à un espace partagé (`/invitation/$invitationId`). Chaque inscription crée l'**espace personnel** de l'utilisateur (hook `user.create.after`), nommé d'après le nom donné ou le préfixe de l'adresse, renommable sur `/settings/espaces`.
  - **Connexion par lien email uniquement** (plugin `magicLink`, `@budget/auth`) : il n'y a **pas de mot de passe** — `emailAndPassword` est absent de la config. Un même geste connecte, inscrit si l'adresse est inconnue (`disableSignUp` laissé à `false`) et **prouve l'adresse**. Cette troisième propriété n'est pas un effet de bord : elle est la contrepartie exacte de `spaces.incoming`, où l'on verrait sinon les invitations d'une adresse qu'il suffirait de déclarer — **ne pas remettre un chemin par mot de passe sans rétablir en même temps une preuve d'adresse**. `expiresIn` vaut 15 minutes (5 par défaut, trop court pour un aller-retour sur téléphone) ; `MAGIC_LINK_MINUTES` est la seule source, annoncée dans l'email et sur les écrans. `/invitation/$invitationId` demande un lien avec son `callbackURL` au lieu d'enchaîner sur `acceptInvitation`, qui n'aurait pas de session — le champ « Votre nom » y reste parce que les autres membres le liront. `settings.save` passe par `adminProcedure` (`user.is_admin`, posé à la main en base) : elle écrase la clé privée Enable Banking de toute l'installation.
- **`/settings/espaces`** (portage de `Espaces.dc.html`, maquette du 2026-08-05) : une carte par espace (compteurs, membres, invitations, bandeau de consentement bancaire), plus l'écran public **`/invitation/$invitationId`**. Le changement d'espace **recharge le document** — le périmètre n'étant pas dans l'URL, le cache des loaders du routeur servirait sinon celui de l'espace quitté ; la bascule reste aussi dans le menu de l'engrenage, à partir de deux espaces.
  - **`organization.is_personal` est une colonne, pas une déduction.** Un espace partagé dont on n'a encore invité personne est indiscernable d'un espace personnel par son nombre de membres, alors qu'il ne se comporte pas pareil : le personnel ne se supprime pas (il naît et meurt avec le compte) et se _convertit_, le partagé se supprime et se quitte.
  - **La conversion est la réponse au seul vrai trou du parcours** : rien ne déplace un compte d'un espace à un autre, donc quand on veut partager un budget déjà constitué, c'est l'espace lui-même qui s'ouvre (`spaces.share` : renomme + `is_personal = false`, rien d'autre ne bouge). Sans retour arrière : le hook d'inscription ne s'exécute qu'une fois, rien ne recrée un espace personnel.
  - **`spaces.incoming` est le pendant de l'inscription ouverte** : les invitations en attente adressées à l'email de la session, en bandeau en haut de `/settings/espaces`. Sans elle, le lien reçu par email serait la seule porte d'un espace partagé. Scopée par `ctx.session.user.email`, jamais par un input — même critère que celui qu'`acceptInvitation` revérifie.
  - **`spacesRouter` n'utilise pas `orgProcedure`** — c'est le seul routeur qui parle _des_ espaces au lieu de travailler _dans_ un espace. Chaque procédure porte donc sa propre autorisation sur l'espace que l'input désigne (`assertOwner` / `assertMember`, `spaces/mutations.ts`), et `spaces.invitation` est carrément **publique** : l'écran d'acceptation doit s'afficher pour quelqu'un qui n'a pas encore de compte. Elle ne renvoie que nom de l'espace, invitant et volumétrie — jamais les membres.
  - **Les mutations écrivent les tables du plugin directement** (Drizzle), sans passer par les endpoints better-auth. Seul `setActive` reste côté client, puisqu'il touche la session.
  - **`expired` n'est pas un statut stocké** : la table ne connaît que pending/accepted/canceled/rejected et une invitation périmée y reste « pending ». Il est dérivé de `expires_at` à la lecture (`invitationStatus`, `spaces/queries.ts`), et `incoming` écarte les périmées par la requête.
  - **Deux gardes sur « Quitter »**, pour deux impasses différentes : le dernier propriétaire laisserait un espace que personne ne peut plus administrer, et son dernier espace laisserait l'utilisateur sans espace actif, donc devant un `FORBIDDEN` sur chaque écran.
  - L'envoi d'email est **minimal et volontairement pauvre** (`packages/auth/src/email.ts`, POST à Resend, aucune dépendance) : deux messages, le lien de connexion et l'invitation. Le module vit dans `@budget/auth` et non dans `@budget/api` parce que better-auth déclenche lui-même le lien de connexion : la dépendance va api → auth, l'inverse serait un cycle. **`send()` a deux régimes selon `NODE_ENV`** : en développement une clé absente écrit le lien dans les logs ; **en production elle lève**, pour que l'écran de connexion ne puisse pas annoncer un email que personne n'a envoyé — sans mot de passe, l'email est l'unique authentification. L'échec n'annule jamais l'invitation créée (elle reste renvoyable).
- **`ctx.authApi` a été retiré du contexte tRPC** : depuis le plugin `organization` son type est assez gros pour que `tsc` renonce à sérialiser celui d'`appRouter` (« inferred type … exceeds the maximum length »), ce qui casse le build de déclarations de `@budget/api`. Ne pas le remettre.

## Commands

Les scripts sont dans `package.json` (`lint` = oxlint, `format` = oxfmt, `test` = vitest par package, `knip`). Ce qui ne s'y lit pas :

- `pnpm -F @budget/tanstack-start dev` — http://localhost:3000, port aligné sur l'URL de callback Enable Banking `http://localhost:3000/callback`.
- `docker compose up -d` — Postgres 17 local (port hôte 5436). **Instance partagée avec l'ancien repo `budget-tracker`** (même conteneur, même volume).
- `pnpm db:generate` puis `pnpm db:migrate`. **`push` a été supprimé le 2026-08-12** : il modifiait la base sans laisser de fichier, donc sans rien à rejouer au déploiement — la prod n'a pas de TTY et sa base ne publie aucun port. Voir « Migrations » plus bas.
- Lint : un seul `.oxlintrc.json` à la racine, catégorie `correctness` seule ; les règles type-aware de l'ancien typescript-eslint (`no-floating-promises`, `no-unsafe-*`) ne sont **pas** actives — le commentaire en tête du fichier dit ce qu'il faudrait pour les rétablir.

**Il n'existe plus de commande CLI métier** : tout se déclenche depuis la webapp, via les mutations tRPC.

- `sync.run` (bouton Synchroniser) — pipeline complet Enable Banking → import → catégorisation LLM. **Never trigger `sync.run` on behalf of the user** : il touche aux sessions bancaires réelles et déclenche une SCA. L'autorisation bancaire se fait sur `/settings/banques`.
- `sync.import` — rejoue l'import des `data/<orgId>/*.json` déjà présents puis la catégorisation, **sans aucun appel bancaire** (ni SCA, ni consommation du quota PSD2). Idempotent, safe à relancer. Aucun bouton de l'app ne l'appelle aujourd'hui.
- **La catégorisation n'a pas de mutation à elle** : elle ne tourne qu'en fin de `sync.run` / `sync.import` (`categorizeUncategorized`, garde `IS NULL`, idempotente). Une transaction qu'aucune catégorie existante ne décrit reste volontairement sans catégorie et sera resoumise au run suivant : un `remaining` qui ne bouge pas signale une branche manquante dans l'arborescence, pas un bug — la réponse est de **créer la catégorie à la main** sur `/settings/categories` (elle sera prise en compte au prochain run), ou de classer la ligne depuis la table (`transactions.updateCategory`). L'analyse LLM qui proposait une arborescence (`categories.suggestions.*`) a été supprimée le 2026-08-24 ; `git log` la rend.

## Base de données — ne jamais confondre avec l'ancien repo

La base de ce projet est **`budget_t3`** (instance Docker **partagée** avec `budget-tracker`, port hôte 5436). Ne JAMAIS lancer une migration (`db:migrate` / `drizzle-kit migrate`) ou toute commande destructive avec une `POSTGRES_URL` pointant sur la base `budget` (celle de l'ancien repo) — vérifier systématiquement le nom de la base dans `POSTGRES_URL`/`.env` avant toute opération de schéma.

### Migrations versionnées (depuis le 2026-08-12)

`packages/db/drizzle/` : un `.sql` par changement, plus `meta/_journal.json`. `pnpm db:generate` écrit le fichier, `pnpm db:migrate` l'applique, et `deploy/deploy.sh` rejoue le même SQL sur la prod **avant** de démarrer le code neuf (schéma neuf + code ancien est inoffensif, l'inverse lève sur chaque écran). La base de prod ne publiant aucun port, le script y accède par un tunnel SSH vers l'IP de bridge du conteneur, le temps du `migrate`.

- **`0000_baseline.sql` décrit le schéma tel qu'il tournait déjà** : il n'a jamais été exécuté nulle part. Les bases existantes ont été « baselinées » — une ligne dans `drizzle.__drizzle_migrations` qui dit « je suis au niveau du socle ». La procédure pour la prod est en tête de `deploy/deploy.sh` ; sans elle, le premier `migrate` rejoue les `CREATE TABLE` et échoue.
- **Le migrateur ne compare que `created_at` au `when` du journal, jamais le hash** (`drizzle-orm/pg-core/dialect.js`) : une migration est « déjà appliquée » si sa date est antérieure à la dernière enregistrée. Éditer un `.sql` déjà appliqué ne le rejoue donc pas — il faut en générer un nouveau.
  - Corollaire, et c'est le piège que `push` n'avait pas : une migration dont le `when` est **antérieur** à la dernière appliquée est ignorée **en silence**, sans erreur ni trace. `db:generate` horodate à l'heure de génération, donc deux branches qui en produisent chacune une, fusionnées dans l'autre ordre, en perdent une. Générer dans l'ordre où ça s'appliquera ; après un rebase qui réordonne des migrations, regénérer plutôt que réordonner les fichiers.
- `pnpm db:migrate` reste **relançable** : sans rien à faire, il ne fait rien.
