# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A personal finance tool (in French — user-facing strings, comments, and category names should be in French) for syncing transactions from 3 personal bank accounts, categorizing them, and generating budget/savings reports.

This is a pnpm + Turborepo monorepo (migrated from the single-package `budget-tracker` CLI tool). It reuses the same business pipeline (Enable Banking → import → categorize → PostgreSQL → transactions table) but split across workspace packages and apps.

## Architecture

- `@budget/db` — schéma Drizzle + `pg`, base **`budget_t3`**.
- `@budget/api` — **tout est piloté depuis la webapp, il n'y a plus aucun script CLI** (`scripts/` a disparu). Organisation en dossiers par domaine sous `src/` :
  - `router/` — adaptateurs tRPC uniquement (`auth`, `transactions`, `categories`, `connections`, `settings`, `sync`) : schéma zod d'entrée + délégation, aucune requête SQL. **Y remettre de la logique métier est une régression.**
  - `banking/` — Enable Banking : `client.ts`, `domain.ts`, `settings.ts`, `connections.ts`, `fetch-transactions.ts`.
  - `transactions/` — `normalize.ts`, `import.ts`, `queries.ts`, `internal-transfers.ts`.
  - **Virements internes** (`transactions/internal-transfers.ts`, spec du 2026-08-03 dans `docs/superpowers/specs/`) — un virement d'un compte suivi à un autre produit deux lignes qui gonflaient entrées _et_ sorties (~20 % des flux affichés). `detectInternalTransfers()` les apparie (`transactions.transfer_pair_id`, auto-référence) après chaque import, sur **toute** la table et non les seules lignes importées : la moyenne de référence porte sur 12 mois, un mois propre comparé à des mois gonflés inventerait un écart. `transfer_source` a le même contrat que `category_source` — `manual` (paire posée ou _retirée_ à la main) n'est jamais réécrit.
    - Le signal décisif est **négatif** : un IBAN de contrepartie renseigné qui ne désigne pas le compte de la jumelle refuse la paire. C'est lui qui sépare un apport interne d'un virement de même montant, le même jour, sur le même compte, venu d'un compte non connecté. `mcc` est vide sur 100 % des lignes : c'est `bank_code` qui sert de veto carte/retrait/prélèvement, et en **liste noire** — SG ne renseigne pas ce champ, une liste blanche l'exclurait de la détection.
    - **Une paire n'est neutralisée que si ses deux jambes sont dans les comptes sélectionnés** (`twinWithinScope`, `transactions/queries.ts`). Seul `bank` est ré-appliqué à la jumelle : les paires vont jusqu'à 3 jours d'écart, donc à cheval sur deux mois — mettre les dates dans le périmètre déplacerait l'artefact sur la frontière de mois au lieu de le supprimer. La propriété que cette règle garantit : le solde affiché égale la variation réelle des comptes affichés, quelle que soit la sélection.
    - Tous les agrégats les écartent **en dur**, sans consulter le param `internes` (qui ne gouverne que le relevé) — sauf `bankCounts`, qui compte des lignes et annonce ce que la table affichera une fois le compte coché : son périmètre est « tous les comptes » alors que le clic va le restreindre, l'exclusion y ferait annoncer 2 pour une table de 3 lignes.
  - `categorization/` — `prompt.ts`, `results.ts`, `similar.ts`, `run.ts`.
  - `categories/` — `queries.ts`, `mutations.ts`, `suggestions/{analyze,apply,state,schema,replace-plan}.ts`.
  - `pipeline.ts` — `performSync` / `performImport`, cross-domaine. `lib/` ne garde que le transverse (`data-dir.ts`, `single-flight.ts`).

  Le sens des dépendances est `router/` → domaines → `lib/`, jamais l'inverse : c'est l'inversion `src/lib/` → `scripts/` qui avait imposé les suffixes `-core`, tous supprimés. Les services importent `db` directement (même singleton que `ctx.db`, voir `trpc.ts`). `lib/single-flight.ts` sérialise les opérations longues : clé `sync` (sync + import) et clé `categorize`, partagée entre la catégorisation déclenchée par le pipeline et celle déclenchée depuis l'UI.

  Deux pièges de configuration liés à la disparition de `scripts/` : `tsconfig.include` vaut `["src"]`, donc `tsc` émet `dist/index.d.ts` (et non `dist/src/…`) — `exports.types` doit suivre, sinon les apps ne résolvent plus les types de `@budget/api`. Et l'exception eslint sur les règles `no-unsafe-*` (code Enable Banking porté, `ebApi` non typé) nomme ses fichiers un par un : ne jamais la remplacer par un glob de dossier, elle exempterait silencieusement du code neuf.
  - **Catégories intelligentes** (arborescence parent/enfant, `categories.parent_id`) : le routeur `categoriesRouter` expose `tree` (arborescence complète) en plus de `list`.
    - **Suggestions** (`src/categories/suggestions/`) — un LLM (`claude-haiku-4-5`) analyse un échantillon de transactions récentes (6 derniers mois, max 500) et propose une arborescence parent → sous-catégories avec les `txnIds` correspondants, exposée via `categoriesRouter.suggestions.{generate,status,accept,apply}` et la page `/categories` (`apps/tanstack-start`). L'état du dernier run est **en mémoire process** (pas de table dédiée) — se perd au redémarrage du serveur, il suffit de relancer l'analyse. L'analyse se déclenche depuis l'UI (`/categories`) — il n'y a plus de commande CLI.
      - **Le prompt part de l'arborescence réelle, et la réponse attendue est l'arbre complet.** `buildAnalysisPrompt(txns, tree)` reçoit `listCategoryTree()` et l'échantillon porte la catégorie actuelle de chaque transaction (`category` / `parentCategory`, `null` pour une orpheline) — sans quoi le LLM ne voit aucun nom existant et propose des **variantes** de l'existant (« Transports » face à « Transport », « Sante » face à « Santé ») : `categories.name` est unique mais sensible à la casse et aux accents, donc rien en base n'arrête le doublon, et l'UI l'affiche comme une nouvelle parente à créer. D'où la règle « réutilise les noms existants au caractère près » en tête des consignes. Le corollaire à ne jamais inverser : la réponse doit rester l'arborescence **entière** (existant repris + nouveautés), **jamais un delta** — `applySuggestions` en mode `replace` traite la proposition comme la nouvelle vérité et supprime tout ce qui en est absent. Un prompt demandant « seulement ce qui manque » ferait de `replace` un bouton de suppression de masse. Côté app, `deriveSuggestions` compare les noms accents/casse/espaces insensibles et, quand une parente existe, fait porter au `GhostBranch` **le nom de la base** et non la chaîne du LLM : c'est lui qui repart dans `accept`, où `upsertCategory` fait un `eq(categories.name, …)` exact. Ce filet ne dépluralise pas (« Frais », « Cours », « Revenus » le mettraient en défaut) — une greffe erronée est silencieuse, un doublon proposé reste visible et écartable.
      - **`accept` (une branche) et `apply` (tout l'arbre) ne sont pas deux tailles du même geste.** `applySuggestions` a un effet de bord qui n'est visible ni dans son nom ni dans l'UI : **dans les deux modes**, y compris `merge` (présenté comme purement additif), toutes les transactions à `category_source = 'llm'` repassent à `category_id = NULL` avant une re-catégorisation complète — seules les `manual` survivent. Un apply coûte donc une passe LLM entière, et son échec est avalé dans un `console.error` (`apply.ts`) alors que l'UI a déjà navigué ailleurs. C'est exactement pourquoi `acceptSuggestion` existe **à côté** et n'appelle pas `applySuggestions` sur un tableau à un élément : elle crée le parent manquant et la sous-catégorie, puis range les `txnIds` **encore `category_id IS NULL`** en `category_source = 'auto'`, sans reset global ni appel LLM. Le garde `IS NULL` est ce qui rend vraie la promesse de l'écran (« rien de ce qui est déjà rangé n'est remis en question ») : l'échantillon analysé contient aussi des transactions déjà classées. Câbler le bouton « Ajouter » sur `apply` défausserait le classement de toute la base à chaque clic.
      - **L'UI de la page est en « Direction C »** (maquette du 2026-07-28) : plus d'écran de relecture ni de bascule fusionner/remplacer — les branches proposées sont posées **dans la liste**, sous la parente concernée, et se répondent une par une (« Ajouter » / « Écarter »). Le rejet est purement local (rien à écrire pour dire non). `deriveSuggestions` (`routes/_authed/categories/-lib/suggestions.ts`) croise la proposition avec l'arbre réel et n'affiche que ce qui manque : une catégorie dont le nom existe déjà n'est jamais une proposition (`categories.name` est unique, et l'analyse re-propose massivement l'existant — c'est même son rôle). Les procédures `apply`/`previewReplace` et leur mode `replace` restent en place et testées, mais **plus aucune UI ne les appelle** : c'est la seule voie de vraie restructuration, à ne pas supprimer sans décision explicite.
      - **Identité d'une parente = couleur + icône**, choisies dans la modale de `/categories` et nulle part ailleurs. `categories.icon` stocke un nom Lucide du jeu fermé `CATEGORY_ICON_GROUPS` (`@budget/shared/src/icons.ts` : noms + mots-clés français, **jamais de composant** — y importer `lucide-react` ferait entrer la librairie dans un package dont la seule dépendance runtime est `zod`) ; la table nom → composant vit côté app (`-components/category-icon.tsx`), explicite plutôt qu'un `import * as lucide` qui embarquerait ~1500 icônes. Même règle que `color` : **seule une parente** en a une (`updateCategoryIcon` le garde), une sous-catégorie se lit dans la famille de son parent. La palette est fermée à 13 teintes pour un nombre illimité de parentes : **une collision de teinte est un état normal**, signalée (pastille « déjà prise », note « même teinte que… ») et jamais interdite — c'est l'icône qui distingue les deux.
    - **Catégorisation few-shot** (`src/categorization/similar.ts`, `prompt.ts`, `results.ts`) — avant l'appel LLM, `findSimilar()` cherche des transactions déjà catégorisées proches (contrepartie exacte > trigrammes `pg_trgm` sur la description > MCC > `bank_code` discriminant en dernier recours) et les injecte comme exemples dans le prompt (`buildFewShotPrompt`). Fallback silencieux vers le prompt générique si aucune similaire trouvée. Nécessite l'extension PostgreSQL `pg_trgm` (voir plus bas). Ces exemples sont des **indices, pas une autorité** : le tier de repli `bank_code`/MCC est très générique (ex. `C2` = « virement reçu » chez SG) et remonte des exemples hétéroclites — le prompt demande explicitement de ne classer par analogie que si la transaction est de même nature.
      - **La similarité prime sur la priorité manuelle dans le tier trigramme.** `manualFirst` (préférer un exemple corrigé à la main) est le premier critère de tri des tiers contrepartie/MCC/`bank_code`, où tous les candidats sont également similaires — mais dans le tier trigramme il ne départage qu'**à l'intérieur d'une bande** de similarité (`round(sim, 1)`). Le remettre en tête y est une régression silencieuse : mesuré sur les données réelles, une correction manuelle faiblement similaire passait devant un quasi-doublon et le meilleur exemple injecté tombait à 69,5 % de bonne catégorie parente, contre 95,8 % avec le tri actuel.
      - **Seuil trigramme à 0,5** (`TRIGRAM_THRESHOLD`), calibré sur les données réelles et non sur une intuition : les libellés bancaires sont dominés par du boilerplate (`CB `, `FACT`, padding, chiffres de date), au point que deux commerçants sans rapport atteignent 0,38. Sous 0,5, l'accord de catégorie parente ne dépasse quasiment pas celui de deux transactions au hasard (19 % contre 15 %). Ce seuil est calibré sur les trois banques actuelles — un établissement au format de libellé moins répétitif le rendrait inutilement strict.
      - **Court-circuit déterministe** (`resolveShortcut`, `results.ts`) — quand au moins 2 similaires partagent la contrepartie de la transaction à classer **et** la même catégorie, elle est catégorisée sans appel LLM (`categorySource = 'auto'`). La comparaison à la contrepartie de la transaction est la garde essentielle : la liste reçue est la **fusion de tous les tiers**, pas seulement du tier contrepartie exacte. Sans elle, deux candidats trigramme partageant une contrepartie _entre eux_ suffisaient à catégoriser d'autorité une transaction qui n'en a aucune — cas majoritaire (57 % des transactions en base), et donc court-circuit de la seule étape capable de rattraper un match faible.
    - **Ne jamais coder en dur un nom de catégorie dans le prompt** (`buildSystemPrompt`) — la catégorisation ne s'appuie que sur les catégories réellement présentes en base. Une règle citant une catégorie absente de la liste (le prompt mentionnait « Revenus », « Autres », « Apport Alex » après un remplacement d'arborescence) fait répondre le LLM hors liste ; la réponse est rejetée et la transaction n'est **jamais** catégorisée, à chaque run. Quand aucune catégorie existante ne convient, le LLM répond `categorie: null` : `partitionResults` sépare ces refus assumés (`declined`) des réponses aberrantes (`rejected`, catégorie inconnue ou id hors lot), et `categorization/run.ts` logue les deux — ne jamais les confondre ni les avaler en silence, c'est ce qui rendait le désalignement invisible.
    - **Les deux process se complètent** : la catégorisation classe avec l'existant, les suggestions créent ce qui manque. C'est `sampleTransactions` (`categories/suggestions/analyze.ts`) qui ferme la boucle, par un **échantillon stratifié** plafonné à `SAMPLE_LIMIT` : d'abord les transactions sans catégorie, **sans fenêtre de date** (une orpheline ancienne reste un trou de l'arborescence) et dans la limite de `UNCATEGORIZED_SAMPLE_SHARE` (30 %), puis complété par les transactions récentes déjà catégorisées, qui donnent le contexte des habitudes réelles. Les deux moitiés sont indispensables et le plafond n'est pas cosmétique : sans la première, les orphelines (~2 % des lignes) seraient évincées dès que le volume dépasse la limite et la boucle ne se refermerait jamais ; sans la seconde, le LLM proposerait un arbre ne couvrant que les orphelines, et le mode `replace` supprimerait tout le reste — `computeReplacePlan` ne protège que les corrections manuelles.

Le même projet porte enfin **« Banques »** (`Banques.dc.html`), porté sur `/banques` + `/banques/ajouter` le 2026-07-29. `Catégories.dc.html` a été repassé le 2026-07-29 : le gabarit de page y a rejoint celui de Banques (conteneur `mx-auto max-w-[1010px]`, titre et bloc de compteurs sur une même rangée, chapô en dessous), et le panneau d'aperçu des transactions — seul composant de l'écran antérieur au portage — a été refait sur le panneau latéral de la maquette.
    - **Trois éléments de la maquette Banques n'ont aucune source et ne sont pas portés.** (1) Le bloc « Synchronisé à 07:12 · aujourd'hui » : _rien en base n'enregistre qu'une synchronisation a eu lieu_ — ni `bank_connections` (validUntil / createdAt / status) ni `app_settings`, et `max(imported_at)` ne bouge que si la synchro a ramené quelque chose, si bien qu'une synchro réussie sans nouveauté (cas courant) laisserait l'écran affirmer « il y a 3 jours » alors que tout marche. Le bloc affiche donc l'état transitoire du bouton, le total importé et la date du **dernier import**, nommée comme telle (`-components/sync-status.tsx`). (2) L'écran intercalaire « Ouverture de … » avec sa barre à 35 % : `connections.start` est suivi d'un `window.location.href`, il n'existe aucune frame où l'app pourrait le rendre — le spinner de la ligne cliquée est toute la vérité disponible. (3) Le « 148 transactions récupérées » et la barre à 58 % de la synchro initiale : `sync.run` est une mutation unique attendue, sans flux de progression — attente indéterminée. Même règle que le score de confiance de la file « À revoir » : ne rien réintroduire ici sans l'avoir d'abord persisté.
    - **Deux éléments de la maquette Catégories n'ont aucune source et ne sont pas portés** (relecture du 2026-07-29). (1) La pastille « N à confirmer » de la ligne d'une parente : `confirmData` est codé en dur (`{ Services: 12, Loisirs: 5 }`), ne correspond à aucun chiffre de `TREE`, et la maquette se contredit — la pastille se pose sur des parentes **existantes** alors que le pied de panneau les compte comme « catégories à confirmer ». La seule donnée qui y ressemblerait vient du plan de remplacement, que la Direction C a justement cessé d'exposer. (2) Le panneau `applying` / `error` / `done` avec sa barre chiffrée : `suggestions.accept` est une mutation par branche, immédiate et confirmée par un toast — il n'y a pas d'application en lot dans cette UI, par construction. Même règle que le « Dernière passe le 26 juil. à 07:12 » du bandeau vert, qui n'est persisté nulle part : le texte affiché à la place ne promet que ce que la base sait.
    - **`Transactions.dc.html` a été repassée le 2026-08-03** : les trois tuiles (Transactions / Débits / Crédits) ont laissé la place au bandeau `KpiBand` (solde en gros à gauche, les deux flux à droite sur des barres proportionnelles — `-components/kpi-band.tsx`) et une colonne de droite est apparue.
      - **Depuis le 2026-08-04, le bandeau et la colonne ne sont plus dans la route : ils sont montés une seule fois par `_revue.tsx`** (voir plus bas), sur le périmètre de la revue. `/transactions` affichait jusque-là les totaux de la _sélection_ (`transactions.totals`, tous filtres appliqués) sous le libellé « Solde de la sélection », avec une moyenne de référence scopée pareil (`historyScope`) et sa propre colonne (`category-side-list.tsx`, `sideScope`) : les trois ont été supprimés, la procédure tRPC `transactions.totals` n'a plus d'appelant. **Conséquence assumée, et c'est la décision, pas un oubli** : filtrer une catégorie ne bouge plus les chiffres au-dessus de la table — le bandeau décrit le mois entier pendant que la table décrit la sélection. Sur `/` l'anneau le rend évident, sur `/transactions` rien ne le dit.
      - La colonne interroge `transactions.byCategory` sur `wholePeriod` **+ `direction: "debit"` forcé**, comme la maquette. Ce n'est pas un réglage qu'on pourrait retirer : sans lui, un seul mois de salaires écrase l'échelle et tous les postes de dépense s'affaissent à un moignon indistinct — mesuré sur les données réelles, `Revenus` à 4 000 € contre un plus gros poste de dépense à 99 €. Deux conséquences voulues : la colonne ne suit pas le sélecteur de sens (elle répond à « où part l'argent »), là où la maquette se vide en passant sur « Crédits » ; et les catégories d'entrée n'y figurent pas — la modale « Filtrer par catégorie » de `RefineBar`, qui liste les deux sens, reste la voie pour les atteindre, et **la seule voie pour retirer le filtre sur `/transactions`**, la colonne repliée sur les sous-catégories n'affichant plus la ligne qui le porte. Masquée sous `lg` sur les deux écrans : elle ne peut pas s'empiler sous la table, qui prendrait toute la hauteur.
      - Le **périmètre de la sélection** (décompte + `describeFilters`) et la **mention des virements internes** retirés des totaux n'ont aucun emplacement dans la maquette — son `scopeLabel` est calculé mais lié à aucun nœud du template — et ne sont plus affichés depuis que le bandeau a cessé de parler de la sélection.
    - `ConnectionSummary.badge` renvoie `{ level: "expired" }` pour **toute** connexion non active : une révoquée y est indiscernable d'une expirée. C'est `status` qu'il faut lire en premier (`-lib/consent.ts`), sinon les copies « n'est plus connectée » et « a été révoquée » fusionnent en silence.
  - `/categories` et `/banques` étant hors du layout `_revue`, ils ont leur propre barre (`~/component/settings-header.tsx`, partagée par les deux écrans de réglages) : même marque et même rangée d'icônes 26 px que `AppHeader`, sans les filtres de période. Le bouton de thème est mutualisé dans `~/component/theme-button.tsx` (`HEADER_ICON_BUTTON` + `ThemeButton`) — il vivait en double dans `AppHeader`. Le jeu de tokens de la maquette est traduit dans les variables shadcn de `src/styles.css` — voir le commentaire du bloc `:root`. Deux points à ne pas défaire : `--primary` porte l'accent de marque (bleu-violet) et non le presque-noir shadcn, et `--accent` reste le rôle _fond de survol_. Le portage applique un facteur ~0,77 aux gouttières et marges de la maquette (24 px → 18, 40 px → 32), jamais aux tailles de texte ni de contrôles : c'est ce qui rend le diff d'une mise à jour de maquette lisible, ne pas re-dériver les espacements au pixel.
  - **`_revue.tsx` porte l'en-tête, la search, le loader des agrégats, le bandeau `KpiBand` et la colonne des postes** ; les routes filles ne rendent que leur écran (l'anneau sur `/`, la table sur `/transactions`) et ne déclarent plus ni `validateSearch` ni les préchargements partagés. C'est `loaderDeps` qui exige la search sur le layout : sans elle, pas de loader partagé. **Ne pas placer sous ce layout une route dont la search diffère de `transactionsSearchSchema`** — l'en-tête et la colonne la lisent via `useRevueSearch()` (`useSearch({ strict: false })`, `AppHeader` étant aussi monté sur `/banques` et `/categories`, le cast ne peut pas devenir strict) et casseraient silencieusement.
    - Le loader du layout construit l'arborescence des postes (`EpureeCategory[]`) et les écarts, et `/` la relit par `useLoaderData({ from: "/_authed/_revue" })` : un enfant ne peut lire que les _données_ du parent, d'où le calcul dans le loader et non dans le composant. Les loaders des routes matchées tournent en parallèle (`Promise.all` dans `load-matches.ts`), il n'y a donc pas de cascade layout → route.
    - **Le poste ouvert est une fonction pure de `search.category`** — la parente filtrée, ou celle qui possède la sous-catégorie filtrée. C'est ce qui dispense le bandeau et la colonne de tout état partagé avec l'écran sous l'`Outlet`, et donc de tout contexte React.
    - Le partage des filtres suit ce qui a un sens sur les quatre écrans. **En-tête** : période, recherche, et le sélecteur de comptes (`BankPicker`, qui porte aussi le bouton Synchroniser). **Par écran** : `RefineBar` (`-components/refine-bar.tsx`) sur `/transactions` (sens + catégorie + à classer) et `/classer` (catégorie seule — l'écran ne parle que de sorties, un sélecteur de sens n'y commanderait rien). La barre de filtres globale du layout a disparu : sur la revue, filtrer une catégorie la portait à 100 % de sa propre répartition.
    - Les filtres restent conservés d'un onglet à l'autre. `/` et `/categorie/$name`, qui n'ont pas de `RefineBar`, affichent donc `<ActiveFilters>` : sans ce rappel, un filtre posé sur la table resterait actif sans rien qui le dise ni aucun moyen de le retirer. Le zoom en exclut `category`, qu'il force lui-même.
    - `bank` accepte **une banque ou une liste** (`@budget/shared`) : le panneau de comptes coche et décoche chaque compte indépendamment. `undefined` = tous les comptes, jamais la liste complète matérialisée — sinon chaque URL porterait les trois banques et ignorerait toute connexion ajoutée ensuite (`selectedBanks` / `toggleBank`, `lib/transactions-search.ts`). Le _roster_ du panneau vient de `transactions.banks` et non de `bankCounts`, qui ne connaît que les banques ayant des transactions sur la période : un compte sans mouvement ce mois-ci en disparaîtrait.
  - La file « À revoir » (`transactions.review`) **n'est pas la maquette à l'identique** : celle-ci affiche un score de confiance par transaction, dont la base n'a aucun équivalent (`category_source` ne connaît que llm / auto / manual). La file est construite sur trois faits vérifiables — pas de catégorie, à classer, sens contraire au sens dominant de sa catégorie. Ne jamais réintroduire un pourcentage de confiance (cartes de `/classer`, pastille « douteux » du zoom, badge de l'onglet) sans le persister d'abord à la catégorisation.
    - Depuis la mise à jour de la maquette du 2026-07-27, cette file n'occupe plus une colonne de la revue mais l'onglet **« À revoir » = `/classer`** : au-dessus les transactions à classer groupées par catégorie, en dessous les « Classements douteux » (`-components/suspect-list.tsx`). Ce partage (`reason !== "a-classer"` pour la seconde liste) est **volontairement plus strict que la maquette**, dont la liste `suspects` inclut aussi le « à classer » et affiche donc la même transaction deux fois sur un écran.
    - Les quatre écrans interrogent `transactions.review` via `reviewScope()` (`lib/transactions-search.ts`) et le `queryClient`, **jamais avec la search brute** : `page`/`sort`/`order` sont inertes côté serveur (`reviewQueue` n'a ni offset ni tri paramétrable) mais entrent dans la clé react-query — une clé par page ferait recharger le badge de l'onglet à chaque « Suivant », et deux clés différentes lui feraient changer de valeur d'un onglet à l'autre. Le plafond de la file (`REVIEW_QUEUE_LIMIT`, `@budget/shared`) est partagé pour que le badge sache afficher « 40+ » plutôt qu'un plafond déguisé en décompte.

L'écran est `-components/epuree-panel.tsx`, réduit depuis le 2026-08-04 au seul `category-ring.tsx` — `kpi-band.tsx` et `breakdown-list.tsx` sont montés par le layout, partagés avec `/transactions`. Ne pas ressusciter les listes supprimées sans demande explicite. La maquette source s'appelle aujourd'hui **`Revue du mois.dc.html`** — c'est l'épurée qui a pris ce nom, l'ancienne étant passée en `Revue du mois (archive).dc.html`.
    - Deux gestes que rien ne distingue dans le nom des états et qui font tout l'écran : `sel` (clic sur un **arc**) fait _descendre_ l'anneau dans les sous-catégories du poste, `opened` (clic sur une **ligne de la colonne**) le met en avant **sans** quitter le niveau des parents. Les deux posent `parent`, et c'est `parent` qui commande le bandeau. Les deux gestes étaient inversés jusqu'au 2026-08-04 : la colonne étant passée dans le layout, elle ne peut plus commander le niveau de l'anneau, c'est donc l'arc qui descend. L'ensemble des états atteignables est le même, seule la correspondance geste → état change.
    - **Le bandeau est `KpiBand`, monté par le layout et partagé avec `/transactions`** : le solde à gauche, les deux flux à droite sur des barres proportionnelles, chacun avec sa pastille d'écart. Dès qu'un poste est ouvert, **les deux rangées de flux disparaissent** (`showFlow: !parent` dans la maquette, ici un prop `flow` optionnel) et le poste (`KpiFocus`) prend toute la droite du bandeau : elles ne se compriment pas à côté de lui, et le solde du mois reste seul en ancre pendant qu'on navigue dans l'anneau. Le prop est un objet `{ revenues, expenses }` et non deux props plus un booléen — un demi-bandeau de flux ne veut rien dire. `KpiBand` ne calcule aucun écart lui-même ; la polarité est fixée par emplacement et non par un prop — une hausse est une bonne nouvelle sur le solde et les entrées, une mauvaise sur les sorties et sur un poste.
    - Il n'y a **pas de bouton de fermeture** : la maquette n'en a pas, et un bouton gardant sa place hors sélection (`invisible`) creuserait un trou permanent à droite d'un `KpiBand` en `flex-1`. On referme en cliquant à côté de l'anneau (`onClick` du conteneur) ou avec Échap (`useEffect` de `EpureePanel`) — ne pas supprimer l'un en croyant l'autre suffisant.
    - `wholePeriod` neutralise `category`, `aClasser` **et `q`** : le bandeau annonce le solde du **mois**, une recherche de libellé dans le relevé ne peut pas le déplacer, et l'anneau perdrait sa répartition pour la même raison qu'avec un filtre de catégorie. Ne restent que la période et les comptes — un périmètre, pas un filtre. Le sens ne compte pas davantage : `byCategory` force le sien, `monthlyHistory` le neutralise.
  - **Vocabulaire** : le terme affiché est « à classer » (il s'appelait « non ventilé » jusqu'au 2026-07-28 ; plus aucune occurrence ne doit subsister). « À classer » = transaction rattachée à une catégorie **parente qui a des sous-catégories**. C'est le search param `aClasser` (prédicat de ligne, `EXISTS` sur `categories`), à ne pas confondre avec `category: "none"` (aucune catégorie du tout) ni avec le drapeau `unallocated` de `transactions.byCategory`, qui est un agrégat — c'est justement pourquoi le param n'est _pas_ nommé `unallocatedOnly`.

D'où l'absence de carte « À classer » sur le zoom d'une catégorie d'entrée — le motif hachuré (`hatchedBackground`, `lib/category-color.ts`) promet un passage par `/classer` que celui-ci ne rendrait pas.     - La liste des catégories de la revue (aujourd'hui `breakdown-list.tsx`) est triée par montant décroissant, sans contrôle : le tri « Écart vs moy. » / « À classer » et son search param `catSort` ont été retirés le 2026-07-28 (avec `categoryAverages`, son seul consommateur). ## Commands

- `pnpm dev` — turbo watch dev (tous les packages/apps en mode dev).
- `pnpm -F @budget/tanstack-start dev` — web app seule, http://localhost:3000 (port aligné sur l'URL de callback Enable Banking `http://localhost:3000/callback`).
- `docker compose up -d` — Postgres 17 local (port hôte 5436). **Instance partagée avec l'ancien repo `budget-tracker`** (même conteneur, même volume).
- `pnpm db:push` — push du schéma Drizzle (turbo task interactive) ; **échoue dans un environnement non-TTY**. Fallback : `pnpm -F @budget/db with-env drizzle-kit push`.
- `pnpm test` — turbo run test (Vitest sur tous les packages).
- `pnpm build` / `pnpm typecheck` / `pnpm lint` — turbo run sur tout le monorepo.

**Il n'existe plus de commande CLI métier** (`import`, `categorize`, `suggest-categories`, `sync` ont été supprimées) : tout se déclenche depuis la webapp, via les mutations tRPC correspondantes.

- `sync.run` (bouton Synchroniser) — pipeline complet Enable Banking → import → catégorisation. **Never trigger `sync.run` on behalf of the user** : il touche aux sessions bancaires réelles et déclenche une SCA. L'autorisation bancaire se fait sur la page `/banques`.
- `sync.import` — rejoue l'import des `data/*.json` déjà présents puis la catégorisation, **sans aucun appel bancaire** (ni SCA, ni consommation du quota PSD2). C'est le remplaçant de l'ancien `pnpm run import` ; idempotent, safe à relancer.
- `categories.categorize` — catégorisation LLM des transactions sans catégorie (idempotent, garde `IS NULL`). Une transaction qu'aucune catégorie existante ne décrit reste volontairement sans catégorie et sera resoumise au run suivant : un `remaining` qui ne bouge pas signale une branche manquante dans l'arborescence, pas un bug — lancer l'analyse de suggestions depuis `/categories`.
- `categories.suggestions.generate` — analyse LLM proposant une arborescence ; n'écrit **rien** en base (ni `accept`, ni `apply` ne sont appelés pour elle). Sûr à relancer.
- `categories.suggestions.accept` — accepte **une** branche proposée : crée la catégorie manquante et range ses transactions encore sans catégorie, sans passe LLM. C'est ce que fait chaque bouton « Ajouter » de `/categories`.

### Seed initial de la table `categories`

Sur un clone neuf, la table `categories` est vide tant qu'elle n'a pas été seedée — la catégorisation fonctionne quand même (no-op silencieux, les transactions restent sans catégorie). Seeder avant la première catégorisation :

```sql
INSERT INTO categories (name, color) VALUES
  ('Revenus', '#00c65a'), ('Logement', '#1447e6'), ('Alimentation', '#b55200'),
  ('Restaurants & bars', '#007857'), ('Transport', '#0084c8'), ('Santé', '#fb64b6'),
  ('Abonnements', '#83cc00'), ('Loisirs & shopping', '#8d56ff'),
  ('Épargne & virements internes', '#fb2c36'), ('Frais & impôts', '#9810fa'), ('Autres', '#94a3b8')
ON CONFLICT (name) DO NOTHING;
```

Ce seed n'est qu'un point de départ : aucun de ces noms n'est référencé par le code (le prompt de catégorisation lit la table, voir Architecture). L'arborescence est censée diverger de cette liste au fil des suggestions appliquées depuis `/categories`.

### Extension `pg_trgm` (catégorisation few-shot)

La recherche de transactions similaires (`categorization/similar.ts`) utilise `similarity()` sur la description, fourni par l'extension PostgreSQL `pg_trgm`. Activée automatiquement sur un volume Docker neuf via `docker-initdb/01-pg_trgm.sql` (monté dans `/docker-entrypoint-initdb.d`, ne s'exécute qu'à la création initiale du volume — voir `docker-compose.yml`).

Sur une instance déjà initialisée avant ce script (ex. le volume partagé avec `budget-tracker`), l'activer manuellement une fois (survit à `db:push`, pas géré par Drizzle) :

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

## Bank data provider: Enable Banking (not GoCardless)

This was a deliberate decision after research, not an assumption — do not revert to GoCardless without re-checking the facts below.

**Why not GoCardless (ex-Nordigen):** confirmed directly on `bankaccountdata.gocardless.com/new-signups-disabled` that GoCardless Bank Account Data is **closed to new signups** — a new project cannot get credentials for it. (If a `secret_id`/`secret_key` from before the shutdown ever surfaces, it might still work, but that can't be relied on for new setup instructions.)

**Chosen alternative: [Enable Banking](https://enablebanking.com).** Verified reasons it fits this project specifically:

- Self-serve signup (just an email — no company/SIRET required to create an account).
- Its **Restricted Production** mode is free, uses real bank data, and its terms explicitly permit _"the personal use of private individuals"_ — this project's exact use case (own accounts, non-commercial). In this mode only accounts you personally link are accessible.
- 2700+ banks across 30 European countries.
- It's the option the wider open-source personal-finance community converged on post-GoCardless-shutdown (e.g. the "Enable Actual" community integration for Actual Budget).
- Trade-off to keep in mind: among mainstream providers, it is close to the _only_ one offering free self-serve access for individuals — Powens, Bridge/Bankin, Tink, Yapily are B2B/sales-led only; Plaid's free tier is US/Canada-only. That's a single-vendor dependency risk (the same kind of risk that just killed the GoCardless setup), acceptable for a hobby project but worth remembering if this ever needs a second provider.
- Regulatory note independent of provider: PSD2 consent must be renewed periodically (~180 days for most EEA ASPSPs) — periodic sync will never be fully unattended long-term; expect to re-authenticate roughly twice a year regardless of provider.
